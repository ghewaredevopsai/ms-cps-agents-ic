How to use this guide

The workshop is trainer-led: Rajesh builds everything live on screen. Nothing here is required of you, and no lab has been provisioned. This guide exists so that if you want to build alongside the demo — on the day or afterwards — you can, without pausing the room to ask what was clicked.

Every demo below is written to the same shape: what it proves → what you need → the steps → the exact text to paste → what you should see → what to do when it breaks.

If you fall behind, stop building and start watching. Every demo states what you should see, so you can read the outcome without having produced it, and the assets are yours to keep — the afternoon is not a race and nothing later depends on your having finished something earlier.

Demo 1.1 Drift, fabrication and the grounding fix AB~10 min
What it proves: the same question, asked three ways, produces three different levels of trustworthiness — and only the grounded version is safe to put near a client deliverable.
You need

Any chat interface to a model you are permitted to use — Microsoft 365 Copilot, Copilot Chat, or the Copilot Studio test pane. The factsheet file for step 3.

Steps
  1. Ask with no context at all. Open a fresh chat and paste prompt A. Note the answer.
  2. Ask again in a new chat. Paste exactly the same prompt A a second time. Compare the two answers word by word.
  3. Now ground it. Attach sample-fund-factsheet.pdf to the chat and paste prompt B. Compare against what the document actually says.
  4. Ask for the impossible. With the file still attached, paste prompt C — it asks for two figures that are not in the document and cannot be worked out from it.
Prompt A — ungrounded
What was the 3-year annualised return of the Northwind Multi-Asset Growth Fund, and what is its total expense ratio?
Prompt B — grounded
Using only the attached factsheet, state the 3-year annualised return of the fund and its total expense ratio.
For each figure, quote the section of the document it came from.
If a figure is not present in the document, reply exactly: not stated.
Prompt C — the refusal test
Using only the attached factsheet, state the fund's tracking error against the benchmark
and its portfolio turnover ratio.
If a figure is not present in the document, reply exactly: not stated. Do not estimate, infer or calculate.
What you should see
  • Prompt A — a fluent, confident answer containing numbers that are wholly invented, because the fund does not exist. The two runs will usually differ.
  • Prompt B — 15.6% and 1.18% (Regular) / 0.62% (Direct), with a pointer to the performance and fees sections. Checkable in seconds.
  • Prompt C — not stated for both. Neither figure appears anywhere in the document, in any form, and neither can be derived from what is there. If you get numbers anyway, you have just watched the failure mode that matters most.
When it does not behave
  • Prompt A returned "I don't know". Good — some configurations are more cautious. Try it without the fund name: "What was the 3-year return of the multi-asset fund we discussed?"
  • Prompt C invented a tracking error. That is the demo working, not failing. Note it — and note that the fix is an instruction, which is exactly what demo 1.3 makes permanent.
  • The file will not attach. Paste the contents of sample-fund-factsheet.txt from the demo assets into the chat instead. It carries exactly the same figures as the PDF, so the demo behaves the same way.
Carry this forward

Prompt B's third line — "if a figure is not present, reply exactly: not stated" — becomes a line in your agent's Instructions in demo 1.3. That single sentence removes most fabrication.

Demo 1.2 A reusable extraction prompt AB~12 min
What it proves: a prompt with named fields and a fixed output shape produces the same table every time — which is what makes the next step automatable. A vague prompt does not.
You need

The same chat interface, with sample-fund-factsheet.pdf attached.

Steps
  1. Ask badly first. Paste the vague prompt. Look at what you get back.
  2. Run it again in a new chat. The shape of the answer will have changed — different headings, different emphasis, different fields.
  3. Now ask properly. Paste the structured prompt. This is the five-part prompt from the slide: role, context, task, format, example.
  4. Run it twice more. Confirm you get the same table each time.
  5. Break it deliberately. Delete the line beginning "If a value is not present" and run once more. Watch the three absent fields fill themselves in.
The vague prompt (run this first, so the contrast lands)
Summarise the key points of this fund factsheet.
The structured prompt
You are an investment consultant preparing a quarterly fund review for an
institutional client - a long-horizon retirement portfolio.

Use only the attached Northwind factsheet (data as of 30 June 2026).
If a value is not present in the document, write: not stated.
Do not estimate, infer or calculate any figure.

Extract exactly these fields:
  fund name, ISIN, share class, fund size (AUM), benchmark, fund manager,
  inception date, TER regular, TER direct, exit load,
  return 1yr, return 3yr, return 5yr, return since inception,
  benchmark 1yr, benchmark 3yr, benchmark 5yr,
  equity allocation, debt allocation, gold allocation, cash allocation,
  top holding name, top holding weight,
  tracking error, portfolio turnover, NAV per unit

Return a markdown table with exactly three columns: field | value | source section.
One row per field, in the order listed above.

Example row:
TER direct | 0.62% | Section 9 Fees
What you should see
  • The vague prompt gives you a readable paragraph or bullet list — useful to a human, useless to a downstream step, and different every run.
  • The structured prompt gives you 26 rows, in your order, with a source column. Run it three times and the table is stable.
  • The last three rows read not stated. Tracking error, portfolio turnover and NAV per unit are deliberately absent from the factsheet — they are there to prove the refusal line is doing work.
  • With the refusal line deleted, watch those same three rows quietly fill with plausible-looking numbers. That is the entire lesson of this demo, and it is worth running twice.
When it does not behave
  • Fields are merged or reordered. Add "Do not merge, rename, reorder or omit any field. If unsure, output the field with value: not stated."
  • You get prose instead of a table. Some interfaces need the format demand repeated at the end. Append: "Output the markdown table and nothing else."
  • The ISIN looks wrong. It should be INF000SAMPLE01 — the factsheet marks it illustrative. If you got a real-looking ISIN, the model invented it.
Carry this forward

Save this prompt. In demo 2.4 the same field list becomes an enforced schema — at which point "not stated" stops being a request and becomes a rule the system checks.

Demo 1.3 Your first agent: the Fund Research Assistant AC~20 min
What it proves: the clever prompt you just wrote stops being a chat message and becomes a thing that exists — named, grounded, shareable, and the same for everyone who uses it.
You need

Copilot Studio access (Track A). The factsheet file. About 20 minutes.

Steps
  1. Go to copilotstudio.microsoft.com and confirm the environment shown top-right is the one you intend to build in.
  2. Select Create → New agent. If offered a describe-it-in-words flow, choose to skip to configure instead — you want to see the four boxes, not have them filled in for you.
  3. Name it Fund Research Assistant and give it the description below.
  4. Paste the Instructions below. This is demo 1.2's prompt, made permanent.
  5. Add Knowledge: under Knowledge, choose Add knowledge → upload sample-fund-factsheet.pdf. Wait until its status shows ready — this takes a minute or two.
  6. Close both doors to the open web. Settings → Generative AI. Switch Allow ungrounded responses to off — that blocks any answer not built from a knowledge source or a tool. Then switch Use information from the Web to off. Both, not one.
  7. Retest before doing anything else. Those two switches are usually enough — verified on a live tenant, where the same question went from a web answer to a cited factsheet answer on the toggles alone. Only if it still cites the web: Topics → System → switch off Conversational boosting, which answers from a generative fallback and is the step almost everyone misses.
  8. Test it in the pane on the right with the three questions below — in a new conversation, always.
Description
Answers questions about fund factsheets for investment consultants. Quotes the
source for every figure and refuses to estimate anything not in the document.
Instructions
You are a research assistant for an investment consulting team.

You answer questions about the fund documents in your knowledge only.

Rules you must follow without exception:
- Every figure you state must come from a document in your knowledge, or from
  an action you called. Never from your own knowledge of the world.
- After every figure, cite the section, page or action it came from.
- If a figure is not in your documents, reply exactly: not stated.
- Never estimate, infer or annualise a figure, and never fill a gap.
- Arithmetic: you may state the difference between two figures you have just
  retrieved, provided you show both of them with their sources in the same
  reply. Everything else that produces a number - totals, averages, weighted
  figures, currency conversion, anything computed across a set of rows - must
  come from an action. If no action provides it, name the action that is
  missing instead of working it out yourself.
- If asked for advice on whether to invest, decline and say that suitability
  is a consultant judgement, not a document lookup.
- Be brief. A consultant is reading this between meetings.

When asked to compare the fund against its benchmark, state both numbers and
the difference, and label the difference as excess return.
Read the arithmetic rule twice — it is the spine of the whole afternoon. A difference between two figures already on screen is checkable by eye, so the agent may state it. A total across ten rows, or a currency conversion, is not checkable by eye — so a system computes it and the agent quotes the system. Demos 2.2 and 2.3 build the actions that make this rule keepable rather than merely stern.
Two other switches live on that same Generative AI page. Leave them alone today, but know they are there. File uploads lets a user attach a PDF, TXT, CSV, XLSX or image to the conversation, up to 15 MB. Code interpreter generates and runs code over an attached file — which is a further deterministic route to a computed number, alongside the actions you build in demos 2.2 and 2.3. The arithmetic rule does not change either way: the figure comes from something that would produce it again tomorrow, and the agent says what produced it. Both switches may be restricted in your tenant.
Test questions
What is the fund's 3-year return versus its benchmark?
What is the tracking error?
Should my client invest in this fund?
What you should see
  • Question 1 — 15.6% fund, 13.1% benchmark, excess return 2.5%, with a citation to the performance section.
  • Question 2 — not stated. The factsheet has no tracking error. This is the agent doing its job.
  • Question 3 — a polite decline that points at consultant judgement. You have just drawn the line between analysis and advice, in configuration rather than in policy.
When it does not behave
  • It answers question 2 with a number. One of the two switches is still on, or the knowledge file has not finished processing. Check both, then retest.
  • It cites a web page even with both switches off. Conversational boosting is still enabled. Turn it off (step 7) and start a new conversation. If a system fallback topic is also swallowing good retrievals, switch that off too while you are debugging, and put it back afterwards.
  • It says it cannot find any documents. The file is still indexing. Wait two minutes. If it persists, remove and re-upload — a PDF over ~200 pages or an image-only scan will not index.
  • It gives advice on question 3. Your Instructions were saved but not applied — use Save, then start a fresh test conversation. The test pane keeps the old configuration within an open conversation.
  • You cannot find those switches. Names and placement move between releases. Alternative: add to Instructions — "If the answer is not in your knowledge documents, do not answer from general knowledge. Reply: not stated." A setting is stronger than a sentence, so keep looking — but the sentence gets you through the demo.
Carry this forward

Keep this agent. Demos 2.1, 2.2, 2.4, 2.5 and 2.6 all extend this agent rather than starting a new one — which is itself the point: an agent grows, a prompt does not.

Demo 1.4 Marking up your own workflow ABC~10 min
What it proves: the judgement, not the tooling, is the scarce skill. Two people with the same tool and different workflow maps will get completely different value out of the afternoon.
You need

Paper, or the table below in a blank document. No AI required — this one is deliberately manual.

Steps
  1. List the steps of one process you personally run — a quarterly review, a manager screen, a client pack. Aim for 6–12 steps, each one a verb.
  2. Time each step honestly, and note how often the whole process runs per year.
  3. Colour each step using the three categories from the slide: prompting helps today, agent-suitable, stays human.
  4. Apply the four criteria to your green steps: repetition, data readiness, value, risk tier.
  5. Write one sentence: "The first agent I would build is ___ because ___." Bring it to the afternoon, or to your own team afterwards.

Usually two things surprise people. First, the steps that cost the most time are rarely the ones that felt hardest. Second, at least one step you assumed needed judgement turns out to be a lookup with a judgement attached to the end of it — and those split cleanly.

Demo 2.1 Generative orchestration, the trace, and proving a fix A~32 min
What it proves: the agent chooses its own path through your knowledge and tools — and when it chooses wrongly, the trace tells you exactly where, so the fix is a sentence rather than a rebuild.
You need

Your Fund Research Assistant from demo 1.3. The second document, manager-update-jul-2026.txt, from the appendix.

Steps
  1. Add a second knowledge source. Save the manager update from the appendix as a .txt or .docx file and upload it alongside the factsheet.
  2. Name it and describe it properly. Give the source a meaningful display name and a one-line description of what it contains. The agent reads both when it decides which source to consult — an untitled upload competes badly against a well-named one, and this costs you nothing.
  3. Mark it as an official source — the ellipsis on the knowledge source → official source. Answers drawn from it are then flagged as coming from an official source. A small thing that matters disproportionately to a reader deciding how far to trust a figure.
  4. Confirm generative orchestration is on — Settings → Orchestration (or the toggle on the agent's Overview). This is what lets the agent decide which source to read.
  5. Ask a question that spans both documents — question 1 below. Neither document answers it alone.
  6. Open the trace. In the test pane, expand the activity / reasoning detail for that answer. Read which knowledge source it consulted, in what order, and what it retrieved.
  7. Now break it on purpose. Ask question 2 — deliberately ambiguous about which period and which plan.
  8. Read the trace again to see what it assumed, then fix it with one instruction (below) and re-ask.
  9. Now prove the fix, instead of believing it. Open the Evaluation tab → New evaluation → Single response → Quick question set. Copilot Studio generates ten questions from your agent's own description, instructions and knowledge. Read them, correct any that are wrong, and run the set.
  10. Change exactly one thing and re-run the identical set. Delete the instruction you added in step 8, run again, compare the two scores. One change per run — change two and a better score tells you nothing about which one earned it.
  11. Export the set to CSV and keep it. This is the file you re-run before every future change, and the artefact that makes a change to a published agent defensible rather than hopeful.
Question 1 — spans both sources
What did the manager say about the gold allocation, and does it match the
allocation shown on the factsheet?
Question 2 — deliberately ambiguous
What is the expense ratio and how has the fund performed?
The one-line fix — append to Instructions
If a question is ambiguous about the period, the share class or the plan
(Regular or Direct), do not choose one silently. Ask which is meant, or state
every variant explicitly with its label.
If your source is a table rather than a document — a Dataverse table, say — you get two more levers on the same screen: per-column synonyms and per-column descriptions. Add the words your team actually uses (tag for asset tag, TER for expense ratio, sleeve for allocation) and retrieval accuracy improves without touching the instructions. Column names are the schema; synonyms are the house vocabulary. Most retrieval complaints about tabular data are really vocabulary complaints.
What you should see
  • Question 1 is answered from both documents, with two citations — the factsheet's 5% gold sleeve and the manager's commentary about it.
  • Question 2, before the fix, silently picks one expense ratio (usually Regular) and one period. Perfectly fluent, quietly wrong for half your readers.
  • After the fix, the agent either asks which you meant or gives both, labelled. Total effort: one sentence.
When it does not behave
  • No trace or activity detail visible. Its placement moves between releases — look for "activity", "reasoning" or a chevron on the answer bubble. Failing that, ask the agent directly: "Which document did you use for that, and which section?"
  • It only ever reads the factsheet. The second file is still indexing, or its name is not descriptive enough. Rename it so the topic is obvious — the agent uses file names when choosing.
  • It answers question 2 correctly first time. Make it harder: "What's the return?" — with four periods on the factsheet, something has to be assumed.
  • The generated questions are poor. Expected — they are generated from your own description and instructions, so a thin description gives thin questions. Fix the description, regenerate, or upload your own CSV of questions with the answers you expect. A test set you wrote yourself is always better than one you accepted.
  • No Evaluation tab. It is a newer surface and may not be in your tenant yet. The discipline survives without it: keep the same ten questions in a file, run them by hand in a new conversation after each change, and record what changed.
Demo 2.2 Calling an external API — and a legacy internal one A~35 minpremium for part 1
What it proves: this is the gap you named. An agent stops being a reader and starts being a participant in your systems the moment it can call one — and a legacy internal endpoint is wired exactly like a public one.
The scenario

The Northwind fund reports in INR. Your client reports in USD. The agent needs the FX rate as at the factsheet date — a live external lookup — and the client's mandate limits, which live in an internal system nobody has an API document for.

Part 1 — the external REST API
  1. Go to make.powerautomate.com → Create → Instant cloud flow → trigger: When Copilot Studio calls a flow. Name it Get FX Rate.
  2. Add two inputs to the trigger: text named ratedate, and number named amountinr.
  3. Add an HTTP action. Method GET. URI: the URL below, with the input appended.
  4. Do the conversion in the flow, not in the agent. Add a Compose action with the expression below — it divides the rupee amount by the retrieved rate.
  5. Add Respond to Copilot with two outputs: text fxjson set to the HTTP body, and number amountusd set to the Compose output.
  6. Save. In Copilot Studio, open your agent → Actions → Add an action → pick your flow.
  7. Give the action a description the agent can route on — text below. This description is how it decides to call your flow, so write it for a reader, not a machine.
  8. Test: ask the agent the FX question below.
The API call
https://api.frankfurter.app/2026-06-30?from=USD&to=INR

A free, no-key FX endpoint. Paste it in a browser tab first to see the raw JSON before you wire it up — always confirm an API works outside the agent before blaming the agent.

The conversion expression — Compose action
div(
  triggerBody()?['amountinr'],
  float(body('HTTP')?['rates']?['INR'])
)

This is the arithmetic rule from demo 1.3 being kept rather than talked about. The agent supplies the rupee figure it read off the factsheet; the flow returns the dollar figure. Nothing multiplies or divides inside the model.

Action description — how the agent knows to use it
Converts an amount in Indian rupees to US dollars at the exchange rate published
for a given date, and returns both the rate and the converted amount. Use this
whenever a value in rupees needs to be expressed in US dollars, or a currency
conversion is requested. Never convert currency yourself - always call this.
Input ratedate must be in YYYY-MM-DD format. Input amountinr is the rupee
amount as a plain number, so Rs 4,820 crore is passed as 48200000000.
Test question
The fund size is in rupees. What is it in US dollars as at the factsheet date?
What you should see — part 1
  • The agent reads Rs 4,820 crore off the factsheet, converts it to 48200000000, and passes that to the action — the one piece of arithmetic it is allowed, because a crore is a unit, not a calculation.
  • It reports roughly USD 557.7 million at a rate of about 86.42, citing the action rather than itself.
  • Ask it "did you work that out yourself?". The correct answer is no, and the trace will confirm it.
No premium connector? The HTTP action is premium. Build the flow anyway, and replace the HTTP action with a Compose action containing fx-response.json from the demo assets (also printed in the appendix). Keep the second Compose that does the division — that is the part which matters. Everything else — the input parameter, the action description, the routing decision, parsing the response, the agent using the result in a sentence — is identical. You lose the live call and keep the entire lesson.
Part 2 — the legacy internal system

No premium needed. This is the honest simulation of an internal endpoint: a flow that returns a fixed JSON payload, exactly as a wrapped legacy service would.

  1. New instant cloud flow, same Copilot Studio trigger, named Get Client Mandate. Input: text, clientid.
  2. Add a Compose action containing client-mandate-CL-4471.json from the demo assets (also printed in the appendix).
  3. Respond to Copilot with text output mandatejson = the Compose output.
  4. Add it to the agent as a second action, with the description below.
  5. Ask the combined question — it needs the factsheet, the mandate and a comparison.
Action description
Looks up a client's investment mandate limits from the internal mandate system.
Returns maximum equity allocation, permitted asset classes and minimum credit
quality. Use whenever a fund must be checked against a client's mandate.
Input clientid is the internal client reference, for example CL-4471.
Test question
Does the Northwind fund's asset allocation comply with the mandate for client CL-4471?
What you should see
  • The agent decides on its own to call the mandate action, then reads the factsheet's allocation section, then compares the two — without being told the sequence.
  • A clear answer: equity at 68% against a 70% mandate limit — compliant, but with only 2 points of headroom, which is exactly the kind of thing a consultant wants flagged.
  • In the trace: two knowledge reads and one action call, in an order the agent chose.
When it does not behave
  • The agent never calls the action. Nine times out of ten the description is too terse. Rewrite it to say when to use it, not just what it does — the agent routes on that sentence.
  • The flow runs but the agent ignores the result. The output is not being returned as text the agent can read. Check the Respond step actually maps the body, and test the flow standalone in Power Automate first.
  • The FX endpoint returns a different date than you asked for. That is correct behaviour — it falls back to the last business day. Good material for a conversation about what your agent should say when data is "close enough".
  • Authentication errors on a real internal API. Expected, and out of scope today — that is a service-principal and gateway conversation with your platform team, and it is the first thing to raise if you take this back to your own environment.
Demo 2.3 Excel and SQL data movement A~25 min
What it proves: numbers come from systems, narrative comes from the model. The moment arithmetic moves into Excel or SQL, a whole class of quiet errors disappears.
You need

holdings.xlsx and benchmarks.xlsx in OneDrive, copied from the demo assets in pre-flight. Both already use a real Excel Table, which is what the connector needs — if you rebuild them by hand from the appendix, select the range and press Ctrl+T first, or the connector will not see them.

Steps
  1. New flow, When Copilot Studio calls a flow, named Get Holdings. No inputs needed.
  2. Add Excel Online (Business) → List rows present in a table. Point it at holdings.xlsx and its table.
  3. Compute the top-five total inside the flow. Add a Compose action with the expression below. This is the step people skip, and skipping it is what pushes the arithmetic back into the model.
  4. Respond to Copilot with two outputs: text holdingsrows (the rows) and number top5weightpct (the Compose output).
  5. Repeat for benchmarks.xlsx as Get Benchmark, with a text input benchmarkname.
  6. Add both actions to the agent with descriptions that say when to use them.
  7. Add the calculation rule below to Instructions — this is what stops the model doing the maths itself.
  8. Ask the three test questions.
The top-five expression — Compose action
add(
  add(
    add(
      add(
        float(first(body('List_rows_present_in_a_table')?['value'])?['weight_pct']),
        float(body('List_rows_present_in_a_table')?['value'][1]?['weight_pct'])),
      float(body('List_rows_present_in_a_table')?['value'][2]?['weight_pct'])),
    float(body('List_rows_present_in_a_table')?['value'][3]?['weight_pct'])),
  float(body('List_rows_present_in_a_table')?['value'][4]?['weight_pct'])
)

Deliberately literal, so you can read what it does at a glance: the weights of rows 1 to 5, added by the flow. The rows arrive already ranked, so the first five rows are the top five. In your own environment this belongs in the query or the workbook — the point is only that it happens somewhere deterministic.

Instructions to append
Never calculate a total, a weighted figure or an average yourself, and never
convert a currency yourself. Retrieve the number using an action and quote it.
You may still state the difference between two figures you have retrieved, as
long as both are shown with their sources.
If a calculation is needed and no action provides it, say which action or data
source is missing, and do not answer with a number.
Test questions
What is the combined weight of the fund's top five holdings?
How did the fund perform against the CRISIL Hybrid 35+65 Aggressive Index over 3 years?
What is the average weight of the fund's top ten holdings?
What you should see
  • Question 1 — 22.9%, quoted from the action's top5weightpct output. Ask "which action produced that?" and it can name one. That is the whole difference between this answer and a plausible one.
  • Question 2 — 13.1% from the benchmark table, 15.6% from the factsheet, and the 2.5% difference labelled as excess return. This one the agent is allowed to subtract, because both operands are on screen with their sources and you can check it by eye.
  • Question 3 — the interesting one. No action returns an average, so the agent should decline and say an averaging action is missing. If it hands you a number instead, the rule is not holding, and you have found the defect this session exists to prevent.
Why question 2 is allowed and questions 1 and 3 are not. Two figures on screen, subtracted, can be checked by any reader in a second. A total across ten rows, or an average, cannot — nobody re-adds the column, so a wrong answer survives review. The line is not "arithmetic is forbidden"; it is "if a reader cannot check it at a glance, a system computes it." That distinction is worth more to your team than any single feature in Copilot Studio.
About the SQL half. The SQL Server connector is premium and most participants will not have a database to point at, so for you this part is watch-only — the wiring is identical to Excel: a flow, a parameterised call, a response, an action description. The trainer runs it against a real database stood up from benchmarks-sql.sql in the demo assets, which creates the benchmark table and the two stored procedures shown on the slide, including usp_GetExcessReturn. That script is yours to keep: it runs on Azure SQL free tier or any SQL Server 2019+, and it is the fastest way to reproduce this half in your own environment. If you want practice today without a database, use benchmarks.xlsx as the stand-in. The lesson is the boundary, not the technology behind it.
When it does not behave
  • Connector cannot see the table. The range is not formatted as a Table. This is the single most common failure in this demo.
  • The agent still does the arithmetic itself. Ask it: "Which action did you use for that figure?" If it cannot name one, strengthen the calculation rule and retest in a fresh conversation.
  • File not found. Excel Online (Business) reads OneDrive for Business and SharePoint, not personal OneDrive. Check which account the connection is using.

Demo 2.7 The agent runs without being asked — the trigger A~20 min
What it proves: this is the one that answers the question you actually asked. Everything so far has been an agent you talk to — useful, but still something a person has to remember to open. A trigger makes it part of the process: a file lands, the work happens, and a human sees a decision rather than a task.
The scenario

A new fund factsheet arrives in a SharePoint library, the way one arrives in your world every quarter. Nobody opens Copilot Studio. Nobody types a prompt. The extraction, the enrichment, the slide plan and the approval request all happen because a file appeared — and the first human involvement is a card in Teams asking a consultant to approve a deck that is already built.

Steps
  1. Create a SharePoint document library (or a folder in one) called incoming-factsheets. A OneDrive folder works just as well if SharePoint is restricted.
  2. New flow — this time an Automated cloud flow, not an instant one. Trigger: When a file is created (properties only), pointed at that library. Name it Factsheet Arrived.
  3. Add Get file content so the flow has the document itself.
  4. Add the Copilot Studio action — in the flow, this is the connector step that invokes your agent and passes the file content plus the instruction below.
  5. Route the agent's reply into the approval you already built in demo 2.6, so the outcome is a card in Teams rather than a message in a chat window.
  6. Test it the honest way: drop sample-fund-factsheet.pdf into the library and then close the browser tab. Come back in two minutes and look at Teams.
  7. Now drop meridian-manager-update.txt in as well — the messy one — and watch what a triggered agent does when the document does not cooperate.
What the flow asks the agent
A new fund document has arrived. Extract the fund record using the schema in
your instructions, enrich it with the mandate and benchmark actions, and produce
a slide plan for a quarterly review.

Do not describe anything as final. Send the plan for approval and report the
outcome. If more than three fields are in needs_review, do not produce a plan at
all - report which fields failed and stop.
Instructions to append
When you are invoked by a process rather than by a person, nobody is present to
answer a follow-up question. So: never ask a clarifying question in that context.
If something is ambiguous, choose nothing, state the ambiguity in needs_review,
and let the approval step put it in front of a human.
What you should see
  • Nothing at all, for about a minute — which is the point. No window is open. No one is waiting.
  • Then an approval card in Teams, carrying a slide plan built from a file you did nothing with except save it in the right place.
  • With the messy document, the agent stops instead: more than three fields in needs_review, so it reports the failure rather than producing a confident, wrong deck. An agent that declines to run is a working agent.
  • In the flow's run history: the whole chain, timestamped, with inputs and outputs you can read back months later when somebody asks where a number came from.
When it does not behave
  • The trigger never fires. SharePoint triggers poll rather than push — the default interval means up to a minute of waiting, and a first run can take longer. Check the flow's run history before you change anything; the most common "broken trigger" is an impatient builder.
  • No Copilot Studio action available in the flow. Feature placement moves between releases and some tenants restrict it. Substitute: have the flow do the extraction by calling the agent's published endpoint, or — simplest — run the same chain from a Scheduled trigger and demonstrate the identical point. Unattended is unattended, whatever started it.
  • It asks a clarifying question and then waits forever. Exactly the failure the appended instruction prevents. Add it, republish, and drop the file again.
  • Everything is blocked in your tenant. Read the steps and watch the trainer. The architecture is the transferable part, and it is unchanged whichever button starts it.
Carry this forward

This is the shape to take to your platform team, because it is the shape that changes a working week. An agent in a chat window saves a person some typing; an agent on a trigger removes a step from the process and puts a human at the decision instead of the keyboard. When you map your own workflow — demo 1.4 — the steps worth automating first are the ones that begin with "when X arrives", because those already have a trigger waiting to be used.

After the workshop — taking this into your own environment

Everything you built today lives in a training environment on synthetic data. Rebuilding it against your own systems is a separate piece of work with real dependencies. These are the five conversations to start, in this order:

  1. An environment. A Power Platform environment your team owns, with dev and prod separated. Ask for this first — everything else waits on it.
  2. Connector approval and DLP. The specific list of connectors your agent needs, and which data groups they sit in. This is the dependency with a queue in front of it, so start it early.
  3. An identity for the agent. How it authenticates to your internal and legacy systems — a service principal, a gateway, or an API wrapper around what exists.
  4. A named owner and reviewer. Not a formality: an agent nobody owns stops being maintained within a quarter, and an approval gate with no time behind it is theatre.
  5. The publishing route. Teams you can usually reach yourself. Microsoft 365 Copilot goes through the organisation catalogue and an administrator's approval queue — so find out who holds that queue and what they need from you. Ask in week one; it is the request that decides your launch date, not your build.
Bring your workflow map from demo 1.4 to that conversation. A request framed as "we want to remove four steps from the quarterly review, here is the map and here is what it needs" lands very differently from "we would like to try Copilot Studio".

Three defects that will find you the first time you write to Dataverse

Nothing today writes to Dataverse — the capstone stages everything in SharePoint on purpose. In your own environment it will be a Dataverse table soon enough, and these three cost an afternoon each the first time:

What you seeWhat is actually wrong
A choice column rejects the write, or silently stores the wrong optionYour form or card collects the choice label as text ("High"); Dataverse stores the choice value as a number. Map it explicitly — set a variable with a Power Fx Switch(Topic.Priority, "Low", 1, "Medium", 2, "High", 3, "Critical", 4, 1) and write the variable, not the label.
