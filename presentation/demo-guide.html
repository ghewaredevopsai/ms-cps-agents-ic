Demo 1.1 A reusable extraction prompt AB~12 min
What it proves: a prompt with named fields and a fixed output shape produces the same table every time — which is what makes the next step automatable. A vague prompt does not.
You need

A bare surface with no Instructions — a scratch Copilot Studio agent with an empty Instructions box is the most reliable, and Copilot chat works if your tenant will fabricate. sample-fund-factsheet.pdf attached. Nothing has been built yet, and that is the point: everything you see here is the prompt doing the work, unaided. In demo 1.8 this same prompt becomes an agent’s Instructions.

Steps
  1. Ask badly first. Paste the vague prompt. Look at what you get back.
  2. Run it again in a new chat. The shape of the answer will have changed — different headings, different emphasis, different fields.
  3. Now ask properly. Paste the structured prompt. This is the five-part prompt from the slide: role, context, task, format, example.
  4. Run it twice more. Confirm you get the same table each time.
The vague prompt (run this first, so the contrast lands)
Summarise the key points of this fund factsheet.
The structured prompt
You are an investment consultant preparing a quarterly fund review for an
institutional client - a long-horizon retirement portfolio.

Use only the attached Northwind factsheet (data as of 30 June 2026).
If a value is not present in the document, write: not stated.
Do not estimate, infer or calculate any figure.

Extract exactly these fields:
  fund name, ISIN, share class, fund size (AUM), benchmark, fund manager,
  inception date, TER regular, TER direct, exit load,
  return 1yr, return 3yr, return 5yr, return since inception,
  benchmark 1yr, benchmark 3yr, benchmark 5yr,
  equity allocation, debt allocation, gold allocation, cash allocation,
  top holding name, top holding weight,
  tracking error, portfolio turnover, NAV per unit

Return a markdown table with exactly three columns: field | value | source section.
One row per field, in the order listed above.

Example row:
TER direct | 0.62% | Section 9 Fees
What you should see
  • The vague prompt gives you a readable paragraph or bullet list — useful to a human, useless to a downstream step, and different every run.
  • The structured prompt gives you 26 rows, in your order, with a source column. Run it three times and the table is stable.
  • The last three rows read not stated. Tracking error, portfolio turnover and NAV per unit are deliberately absent from the factsheet — they are there to prove the refusal line is doing work. Demo 1.8 deletes that line and shows what fills the gap.
When it does not behave
  • Fields are merged or reordered. Add "Do not merge, rename, reorder or omit any field. If unsure, output the field with value: not stated."
  • You get prose instead of a table. Some interfaces need the format demand repeated at the end. Append: "Output the markdown table and nothing else."
  • The ISIN looks wrong. It should be INF000SAMPLE01 — the factsheet marks it illustrative. If you got a real-looking ISIN, the model invented it.
  • Step 5 changed nothing — the fields still read not stated. Expected in Microsoft 365 Copilot chat with a file attached: it will not invent a field value whichever instruction you delete, and it emits not stated on its own as its convention for an absent field. Deleting the second guard as well makes no difference. Run step 5 against a Copilot Studio agent with Allow ungrounded responses on, or present it as a walkthrough rather than a live result.
Carry this forward

Save this prompt. In demo 2.4 that same discipline becomes an enforced schema over a slightly different field list — at which point "not stated" stops being a request and becomes a rule the system checks.

Demo 1.2 Manager update → the house question list AB~5 min
What it proves: the five parts are not specific to factsheets. Same anatomy, a different document, and a fixed question list — which is what makes manager A and manager D comparable at all.
You need

The same bare surface as demo 1.1 — still no Instructions — with meridian-manager-update.txt attached (it is in demo-assets/). It is also the second knowledge source on the Fund Research Assistant, but run this one outside that agent for the same reason as 1.2.

Steps
  1. Ask badly first. "What does this manager update say?" You will get the manager’s own emphasis, in the manager’s own order.
  2. Now paste the structured prompt. Same five parts as the slide, pointed at a different job.
  3. Read the headings, not the prose. They are in your order now, and one of them should say Not addressed.
The prompt
You are an investment consultant reviewing a manager's quarterly update
for an institutional client.

Use only the attached manager update (July 2026). If the update does not
address something, write: not addressed. Do not infer it from tone.

Answer the house question list, in this order:
  1. what changed in the team
  2. what changed in the process
  3. what drove performance this quarter
  4. the manager's own explanation of the worst quarter

One heading per question. Two sentences maximum under each.
Write "Not addressed" wherever the update is silent.

Example:
Team - Two analysts left the credit desk in May; no replacement named. Section 3
What you should see
  • Four headings, in the order you asked for — not the order the manager wrote in.
  • At least one Not addressed. That is the finding: the thing the update quietly skipped is now visible instead of absent.
  • Run it against a second manager update and the two are comparable line for line. That is the whole point of a house list.
When it does not behave
  • It answers in the manager’s order. Repeat the constraint at the end: "Answer the four questions in the order given, even where the update covers them in a different order."
  • It infers a reason from tone. The CONTEXT line is doing the work. Strengthen it: "If the update does not state a reason, write: not addressed. Do not construct one."
Demo 1.3 Meeting notes → decisions, actions, owners AB~5 min
What it proves: the FORMAT line is the whole value here. Three lists with an owner-and-date rule turn a readable summary into a record somebody can be held to.
You need

Nothing attached. Same bare surface — paste the synthetic notes below, then the prompt underneath them.

Steps
  1. Paste the notes. They are deliberately messy, the way real notes are.
  2. Paste the prompt. Note that it demands an owner and a date on every action line.
  3. Count the not stated entries. Those are the actions that would have quietly gone nowhere.
The notes to paste first
IC meeting, 14 July. Present: three of five.
Northwind - 3yr 15.6% vs benchmark 13.1%. Committee comfortable. Equity 68%,
mandate ceiling 70%, agreed to keep watching but no action for now.
Someone to get the latest fee schedule off the manager - direct plan TER
looked like 0.62% but nobody had it in writing. Before end of September.
Question raised about whether the gold sleeve is still doing anything.
Parked. Agreed to revisit the whole allocation at the October meeting.
Chair asked for the Q3 pack a week earlier than usual this time.
The prompt
You are the secretary of an investment committee, writing the record
for people who were not in the room.

Use only the notes above. Do not add context you believe to be true but
that nobody actually said.

Separate the notes into three lists: decisions taken, actions agreed,
and questions left open.

Three headed lists. Every action line carries an owner and a date. Where
either is missing, write: owner not stated, or: date not stated.

Example:
Action - Request the fee schedule from the manager | Owner: not stated | By: 30 Sep
What you should see
  • Three lists, and the split is cleaner than the notes felt.
  • The fee-schedule action comes back as owner not stated. In the notes it reads as agreed; in the record it reads as nobody’s job. That is the demo.
  • The gold-sleeve question lands under open, not under decisions — "parked" is not a decision.
When it does not behave
  • It invents an owner. Usually the chair. Add: "Never attribute an action to a person who is not named in the notes."
  • It merges decisions and actions. Add one line of definition: "A decision is a conclusion reached. An action is something a named person must do."
Demo 1.4 Holdings extract → data-quality check AB~5 min
What it proves: the CONTEXT line holding the arithmetic back. This is the task where totalling the column is most tempting and a wrong total is least visible.
You need

Same bare surface. holdings.xlsx from demo-assets/, or just paste half a dozen rows of it — either works.

Steps
  1. Paste the prompt with the holdings rows.
  2. Check what it did not do. It should flag rows and refuse to total the weight column.
  3. Optional, ~30 seconds: delete the sentence beginning "Do not calculate" and run again. Watch a total appear that nobody asked for and nobody will re-add.
The prompt
You are a portfolio analyst checking a holdings file before it is used
in a client report.

Use only the rows in the attached extract. Do not calculate totals,
averages or weighted figures, and do not convert currencies.

Flag: duplicate identifiers, missing sector or currency, blank weights,
and any row whose currency differs from the fund's stated currency.

Return a table - row number | field | what is wrong | why it matters.
Nothing else: no summary, no total row.

Example:
14 | currency | blank | cannot be aggregated or converted
What you should see
  • A table of flagged rows, and no total anywhere.
  • If a total appears, the CONTEXT line was dropped or overridden. That is worth showing deliberately — the number will look entirely reasonable.
  • This is the same tiered rule as the rest of the day: the model may state a difference between two figures it can show you; totals, averages and weighted figures come from an action.
When it does not behave
  • It totals the weights anyway. Move the refusal to the last line of the prompt. Position matters more than wording here.
  • It invents a sector for a blank cell. Add: "A blank cell is a finding, not a gap to fill."
Demo 1.5 Draft commentary → house tone, figures frozen AB~5 min
What it proves: one worked line settles tone faster than a style guide — and that a rewrite is the easiest place in the day to lose a number without noticing.
You need

Nothing attached. Same bare surface — paste the draft below, then the prompt.

Steps
  1. Paste the draft. It is deliberately written in the wrong voice.
  2. Paste the prompt, including the worked example line.
  3. Compare the figures, not the prose. Every number in the output should be byte-identical to the draft.
The draft to paste first
The fund had a truly excellent three years, delivering a stellar 15.6%
annualised and comfortably crushing its benchmark's 13.1%. Equity exposure
ended the period at a healthy 68%, and we remain very confident that this
positioning will continue to reward patient investors going forward. Fees
remain highly competitive at 1.18% regular and just 0.62% direct.
The prompt
You are writing quarterly commentary in your firm's house voice
for an institutional client.

Use only the figures in the draft above. Do not change, round or
re-express any number, and do not add a figure that is not already there.

Rewrite the draft in house tone: plain, specific, no superlatives,
and no forward-looking claims.

Three paragraphs, 120 words maximum each. Every figure exactly as written.

Example of house tone:
The fund returned 15.6% over three years, against 13.1% for the benchmark.
What you should see
  • “Truly excellent”, “stellar”, “crushing” and “healthy” all gone; the sentences got shorter and more specific.
  • The forward-looking claim disappears — "we remain very confident this positioning will continue to reward" is exactly the sentence a consultant cannot sign.
  • 15.6, 13.1, 68, 1.18 and 0.62 all survive untouched. Check them one by one. This is the failure to watch for, because rounding reads as tidying.
When it does not behave
  • 15.6% becomes “approximately 16%”. The most common failure, and the most plausible-looking. Repeat the constraint last: "Quote every figure exactly as it appears. Do not round."
  • It keeps a superlative you did not notice. Give it the list: "Remove: excellent, stellar, strong, robust, healthy, comfortably, significantly."
Demo 1.6 Drift, fabrication and the grounding fix AB~10 min
What it proves: the same question, asked three ways, produces three different levels of trustworthiness — and only the grounded version is safe to put near a client deliverable.
You need

Any chat interface to a model you are permitted to use — but prefer the Copilot Studio test pane. On a cautious tenant Microsoft 365 Copilot invents a figure close to the real one (~17% against a true 15.6%) and the contrast barely registers; an agent typically invents 5–7%, which is visibly wrong. The factsheet file for step 3.

Steps
  1. Ask with no context at all. Open a fresh chat and paste prompt A. Note the answer.
  2. Ask again in a new chat. Paste exactly the same prompt A a second time. Compare the two answers word by word.
  3. Now ground it. Attach sample-fund-factsheet.pdf to the chat and paste prompt B. Compare against what the document actually says.
  4. Ask for the impossible. With the file still attached, paste prompt C — it asks for two figures that are not in the document and cannot be worked out from it.
Prompt A — ungrounded
What was the 3-year annualised return of the Northwind Multi-Asset Growth Fund, and what is its total expense ratio?
Prompt B — grounded
Using only the attached factsheet, state the 3-year annualised return of the fund and its total expense ratio.
For each figure, quote the section of the document it came from.
If a figure is not present in the document, reply exactly: not stated.
Prompt C — the refusal test
Using only the attached factsheet, state the fund's tracking error against the benchmark
and its portfolio turnover ratio.
If a figure is not present in the document, reply exactly: not stated. Do not estimate, infer or calculate.
What you should see
  • Prompt A — a fluent, confident answer containing numbers that are wholly invented, because the fund does not exist. The two runs will usually differ.
  • Prompt B — 15.6% and 1.18% (Regular) / 0.62% (Direct), with a pointer to the performance and fees sections. Checkable in seconds.
  • Prompt C — not stated for both. Neither figure appears anywhere in the document, in any form, and neither can be derived from what is there. If you get numbers anyway, you have just watched the failure mode that matters most.
When it does not behave
  • Prompt A refused instead of inventing. Common — a tenant with web and enterprise search will look, find nothing, and decline. Dropping the fund name does not help; it refuses again. Ask for an estimate outright: "It is a well-known Indian multi-asset growth fund. Give me your best estimate of its 3-year annualised return and total expense ratio. Approximate figures are fine." It will hedge the numbers as an informed estimate — say that out loud, because the caveat is exactly what gets stripped when the figure reaches a deck.
  • Prompt C invented a tracking error. That is the demo working, not failing. Note it — and note that the fix is an instruction, which is exactly what demo 1.8 makes permanent.
  • The file will not attach. Paste the contents of sample-fund-factsheet.txt from the demo assets into the chat instead. It carries exactly the same figures as the PDF, so the demo behaves the same way.
Carry this forward

Prompt B's third line — "if a figure is not present, reply exactly: not stated" — becomes a line in your agent's Instructions in demo 1.8. That single sentence removes most fabrication.

Demo 1.8 Your first agent: the Fund Research Assistant AC~31 min
What it proves: the clever prompt you just wrote stops being a chat message and becomes a thing that exists — named, grounded, shareable, and the same for everyone who uses it.
You need

Copilot Studio access (Track A). The factsheet file. About 31 minutes.

First, the three-click version — 3 minutes

Before building anything, see what you get without Copilot Studio. This is the rung most of the room can reach on their own, and the contrast is what makes the next 28 minutes worth sitting through.

  1. Open a SharePoint document library holding a few fund documents. Use Add an agent (wording varies) from the library itself.
  2. Name it, write one sentence describing who it is for, and save. There is no canvas and nothing to configure.
  3. Ask it two of the test questions below, then share the link with someone.
What to point out while it answers. It works, it cites, it is shareable, and it took a minute — that is a genuine result and it is the right first thing for most people to build. Then ask it the third test question, the one needing a benchmark figure, and watch it fail: it can only read that library. It cannot call the mandate system, cannot run when nobody asks, cannot produce a deck, and offers no trace to read when it is wrong. Those four sentences are the reason the rest of this demo exists. Participants who want this for their own libraries have it as Part 3 of the reference pack.
Steps
  1. Go to copilotstudio.microsoft.com and confirm the environment shown top-right is the one you intend to build in.
  2. Select Create → New agent. If offered a describe-it-in-words flow, choose to skip to configure instead — you want to see the four boxes, not have them filled in for you.
  3. Name it Fund Research Assistant and give it the description below.
  4. Paste the Instructions below. This is demo 1.1's prompt, made permanent.
  5. Add Knowledge: under Knowledge, choose Add knowledge → upload sample-fund-factsheet.pdf. Wait until its status shows ready — this takes a minute or two.
  6. Close both doors to the open web. Settings → Generative AI. Switch Allow ungrounded responses to off — that blocks any answer not built from a knowledge source or a tool. Then switch Use information from the Web to off. Both, not one. Note where this switch goes next: demo 2.4 turns Allow ungrounded responses back on, and cannot run without it — the pair of demos is the clearest illustration all day of what “grounded” actually enforces, so plan to toggle it live rather than leaving it one way all day.
  7. Retest before doing anything else. Those two switches are usually enough — verified on a live tenant, where the same question went from a web answer to a cited factsheet answer on the toggles alone. Only if it still cites the web: Topics → System → switch off Conversational boosting, which answers from a generative fallback and is the step almost everyone misses.
  8. Test it in the pane on the right with the three questions below — in a new conversation, always.
  9. Now make one behaviour non-negotiable. Question 3 was refused by a sentence in Instructions — guidance the model weighs against everything else you wrote. For the things compliance signs off, that is not strong enough. Topics → + Add a topic → From blank, named Advice refusal.
  10. Describe when the topic applies. There is no longer a trigger-phrase list: a blank topic's trigger is "The agent chooses" plus a free-text "Describe what the topic does" box. Put the six phrases below into that description as example questions, and add the narrowing sentence so it does not swallow document lookups. They match on meaning, so you need not enumerate every phrasing.
  11. Add a Message node and paste the refusal wording below. Nothing on this path is generated, so nothing on it can be re-worded. Save.
  12. Retest in a new conversation, asking three ways — "should we buy this", "is this a good fund", "would you recommend it". Compare with step 8.
  13. Break it deliberately. In this agent’s Instructions, delete the line beginning "If a value is not present", turn Allow ungrounded responses on, and re-run demo 1.1’s structured prompt. Watch tracking error, portfolio turnover and NAV per unit quietly fill with plausible numbers that change every run. Put the line back afterwards.
Description
Answers questions about fund factsheets for investment consultants. Quotes the
source for every figure and refuses to estimate anything not in the document.
Instructions
You are a research assistant for an investment consulting team.

You answer questions about the fund documents in your knowledge only.

Rules you must follow without exception:
- Every figure you state must come from a document in your knowledge, or from
  an action you called. Never from your own knowledge of the world.
- After every figure, cite the section, page or action it came from.
- If a figure is not in your documents, reply exactly: not stated.
- Never estimate, infer or annualise a figure, and never fill a gap.
- Arithmetic: you may state the difference between two figures you have just
  retrieved, provided you show both of them with their sources in the same
  reply. Everything else that produces a number - totals, averages, weighted
  figures, currency conversion, anything computed across a set of rows - must
  come from an action. If no action provides it, name the action that is
  missing instead of working it out yourself.
- If asked for advice on whether to invest, decline and say that suitability
  is a consultant judgement, not a document lookup.
- Be brief. A consultant is reading this between meetings.

When asked to compare the fund against its benchmark, state both numbers and
the difference, and label the difference as excess return.
Read the arithmetic rule twice — it is the spine of the whole afternoon. A difference between two figures already on screen is checkable by eye, so the agent may state it. A total across ten rows, or a currency conversion, is not checkable by eye — so a system computes it and the agent quotes the system. Demos 2.2 and 2.3 build the actions that make this rule keepable rather than merely stern.
Two other switches live on that same Generative AI page. Leave them alone today, but know they are there. File uploads lets a user attach a PDF, TXT, CSV, XLSX or image to the conversation, up to 15 MB. Code interpreter generates and runs code over an attached file — which is a further deterministic route to a computed number, alongside the actions you build in demos 2.2 and 2.3. The arithmetic rule does not change either way: the figure comes from something that would produce it again tomorrow, and the agent says what produced it. Both switches may be restricted in your tenant.
Describe what the topic does — the Advice refusal topic

A blank topic no longer takes a list of trigger phrases. It takes one free-text description of what the topic does, and the agent routes to it from that. Write the condition, not a sample question — then test it with several phrasings, because the description is doing the work a phrase list used to do.

Fires when the user asks whether to invest in, buy, recommend or allocate to
a fund, or whether one is suitable for a client - any question seeking an
investment judgement rather than a document lookup.
Message node — the wording, fixed
I can't advise on whether to invest. Suitability depends on the client's
mandate, risk tolerance and existing allocation - that is a consultant
judgement, not a document lookup.

I can give you what the documents say: performance against the benchmark,
the allocation, the risk figures and the mandate limits. Ask me for any of
those and I will cite the source.
Instructions or a topic? The test is who has to defend the wording. Instructions are the right home for almost everything — they are how the agent adapts to a question you did not anticipate. A topic is right when the answer must be identical every time and somebody outside the team signs it off: the advice refusal, a regulatory disclaimer, the escalation path on a mandate breach. Three topics is healthy for an agent this size; thirty means you have rebuilt a decision tree. Note that the agent still chooses the topic, so the description you give it matters as much as the message inside it.
Test questions
What is the fund's 3-year return versus its benchmark?
What is the tracking error?
Should my client invest in this fund?
What you should see
  • With the refusal line deleted, the three deliberately-absent fields fill with plausible-looking numbers — different ones each run. That contrast is the reason demo 1.1 ran on a bare surface first: you have now seen the same prompt with and without an Instructions box behind it.
  • Question 1 — 15.6% fund, 13.1% benchmark, excess return 2.5%, with a citation to the performance section.
  • Question 2 — not stated. The factsheet has no tracking error. This is the agent doing its job.
  • Question 3 — a polite decline that points at consultant judgement. You have just drawn the line between analysis and advice, in configuration rather than in policy.
  • Question 3, after the topic — the same words, whichever way you asked. Before, the decline was polite and slightly different every time; after, it is a fixed statement compliance can read once and approve once. That is the whole argument for topics.
When it does not behave

The banner: because the agent uses Microsoft authentication, only Teams, Microsoft 365 and SharePoint are available — though every other tile, WhatsApp and Slack included, is still on the page, and Web app will hand you an SDK connection string if you ask it to. That placeholder is the first thing a colleague sees.

With Authenticate with Microsoft on, knowledge results trim to each asker's own permissions — a colleague who cannot open a file cannot be cited to it. On a governed tenant you may find No authentication and Authenticate manually greyed out altogether, and Multi-tenant support disabled — the decision taken above your head, which is the point rather than a disappointment.

Then read its Data & tools tab out loud: knowledge is listed with a Sensitivity label column, but Tools reports "No tools configured" for an agent with seven, and Permissions reports none from Entra ID. The person approving your agent cannot see that it calls five flows and an outside endpoint under your credentials — so the reviewer's checklist has to come from you, which is what the table below is for. Without admin rights — the normal case — find out who holds that queue. They are on your critical path, and the queue is not short.

Add Approvals → Create an approval — not Start and wait for an approval. Then Respond to the agent with two text outputs: status, a fixed Pending approval, and approvalid, set to the action's Approval ID. Publish the flow.

And on the tool's Inputs, change approver from Dynamically fill with AI to Custom value with a real address: left on AI-fill the agent invents a plausible address and the approval silently goes nowhere.

It returns as soon as the request is sent, so the outcome is not known yet: report that approval is pending and never describe the output as approved."

  12. Ask the agent for a client-ready deck. It should come back in a few seconds with an approval id and the word pending — not hanging, and not calling the deck final.

What you should see
  • The agent, in Teams, in your own sidebar — the moment it stops being a project and becomes a tool.
  • The agent answering in seconds, not hanging: an approval id, the status pending approval, and a plain statement that the deck is not client-ready yet.
  • An approval card carrying the deck summary the agent itself wrote — slide count, what each slide holds, and which action every figure came from.

When it does not behave
  • Teams channel greyed out. The agent is not published, or your tenant restricts Teams app publishing. Publishing to the test channel still demonstrates it.
  • The agent's call fails with ActionResponseTimedOut, or an HTTP 504. You used Start and wait for an approval. A flow called by an agent has roughly 100 seconds to answer; waiting on a human blows straight through it. The giveaway in the run history is cruel: the approval step succeeded, and only Respond to the agent failed — the human answered, but the agent had already hung up. Swap in Create an approval.
  • The agent never appears in M365 Copilot. Two usual causes now that Teams and M365 Copilot share one channel: the catalogue request is still awaiting an administrator, or the audience you chose does not include you. Check both before rebuilding anything.
  • Approval never arrives. Most often the approver input was left on Dynamically fill with AI and the agent invented an address. Otherwise check the run history in Power Automate — the flow, not the agent, is where the truth is.
  • The agent reports the rejection but no reason. Not the model being unhelpful — the flow. approvercomments is bound to responseSummary, which never contains the comment; point it at responses[0].comments instead.
  • The agent calls output "final" without approval. Your rule is in Instructions but the conversation started before you saved. New conversation, retest.
Demo 2.7 The agent runs without being asked — the trigger A~26 min
What it proves: this is the one that answers the question you actually asked. Everything so far has been an agent you talk to — useful, but still something a person has to remember to open. A trigger makes it part of the process: a file lands, the work happens, and a human sees a decision rather than a task.
The scenario

A new fund factsheet arrives in a SharePoint library, the way one arrives in your world every quarter. Nobody opens Copilot Studio. Nobody types a prompt. The extraction, the enrichment, the slide plan and the approval request all happen because a file appeared — and the first human involvement is a card in Teams asking a consultant to approve a plan. Approve it and the deck renders itself — PowerPoint, then PDF, then an email with the PDF attached, in about fifteen seconds. Nothing client-facing exists until somebody has said yes.

Steps
  1. Create a SharePoint document library (or a folder in one) called incoming-factsheets. A OneDrive folder works just as well if SharePoint is restricted.
  2. New flow — this time an Automated cloud flow, not an instant one. Trigger: When a file is created (properties only), pointed at that library. Name it Factsheet Arrived.
  3. No Get file content step is needed — this trigger already returns File content, File name and File path among its outputs. One step fewer than you would expect.
  4. Call the agent. The action is not called "the Copilot Studio action": it is Microsoft Copilot Studio → Execute Agent and wait. Pick your agent, then click Show all on the advanced parameters to reveal Message, and put the instruction below there with the trigger's File name token inside it. First use asks you to create a connection.
  5. Put the approval in the flow, not in the agent's hands. Add Approvals → Start and wait for an approval — Approve/Reject – First to respond, assigned to yourself, Details set to the agent's reply. This is not a step backwards from demo 2.6: told to "send the plan for approval" with nobody watching, the agent tends to narrate the approval instead of calling the tool — writing "Slide plan (pending approval)", or even replying that no approval system was found in its knowledge. No card is created. A human gate must not depend on the model choosing to use it.
  6. And notice you are allowed to wait here. Demo 2.6 had to use fire-and-forget because a flow called by an agent gets roughly 100 seconds. Nothing is calling this flow — a file did — so it can block on a person for days. On a live run it sat on this step for 5 hours 45 minutes and resumed correctly the moment the card was answered. Same connector, same action, opposite verdict, and the only thing that changed is who started the flow. That is the most transferable sentence in the afternoon: what a step is allowed to do depends on what is waiting behind it.
  7. Everything after the gate. Add a Condition — the approval's outcome is equal to Approve — and put six actions in the True branch, in this order. The trainer's copy is already built: walk it rather than building it live unless the session is running early.
    • Compose — the slide plan, split out of the agent's reply between the two markers.
    • HTTP — POST that plan to the renderer endpoint.
    • Create file — review-deck-<timestamp>.pptx, content = the HTTP body. Timestamped, not fixed: a constant filename overwrites yesterday's deck, and it did — five successful runs once produced one file.
    • Convert file — target type PDF, File = the Id the Create file step returned.
    • Create file again — the .pdf, named by swapping the extension on the first file's name.
    • Send an email (V2) — attachment Name = the PDF's name, Content = the Convert file body.
    Then give the False branch one action of its own — another Send an email (V2), saying the deck was rejected, that no PDF was produced and nothing has gone to the client, and pointing at the run history for the reviewer's comment. Without it a rejected run ends silently and nobody is told, which is the kind of gap that only shows up in production. Say why the reason is not in the email itself: getting it there means responses[0].comments, not responseSummary — the same trap as demo 2.6 step 12 — and the run history has it either way.
  8. Test it the honest way: drop sample-fund-factsheet.pdf into the folder and then close the browser tab. Come back in three to five minutes and look at Teams. The agent's leg is the steady part — about two and a half minutes, run after run. The polling trigger in front of it is the variable one, taking anything from the same minute as the drop to a couple of minutes. Budget the longer figure.
  9. Now drop meridian-manager-update.txt in as well — the messy one — and watch what a triggered agent does when the document does not cooperate.
  10. Change the trigger, and nothing else. Open the same flow, delete the trigger step, and put a different one in its place. Everything downstream — call the agent, wait for approval, render, convert, email — is untouched. Do it twice, with the two below.
The two other triggers worth building
  • Recurrence — runs on a date, not an event. Set it to the first business day of the quarter, because your quarterly review is a calendar obligation: nobody drops a file to start it, the date arrives. Over a list of funds, this is the difference between reviewing one fund when asked and having drafted all twelve before anyone sits down.
  • When a new email arrives (V3) — filtered to a folder or sender, has attachment set, include attachments on. The honest one: manager updates, capital-call notices and revised factsheets arrive in an inbox, not a library. A shared mailbox a flow watches is usually a shorter conversation than a new SharePoint site.
The trigger is a swap, not a rebuild. A file arriving, a date, an email, a row changing, an approval completing, another agent calling — each is one dropdown, and everything from demos 2.2–2.6 runs unchanged behind it. You are not looking for work that suits Copilot Studio; you are looking for the sentence “when X arrives, someone has to…”.
What the flow asks the agent
A new fund document has arrived in the incoming-factsheets folder: [File name].
Extract the fund record using the schema in your instructions, enrich it with the
mandate and benchmark actions, and produce a slide plan for a quarterly review.

Produce the plan only: do not call the deck-building tool, because this process
renders the deck itself after a human has approved the plan.

Do not describe anything as final; the flow will send this for approval. Do not
state an approval id - you will not have one. If more than three fields are in
needs_review, do not produce a plan at all - report which fields failed and stop.

When you do produce a plan, end your reply with the slide plan as raw JSON
matching the slide-plan schema in your instructions, wrapped exactly in the
markers ===PLAN_JSON_START=== and ===PLAN_JSON_END=== with nothing after the
closing marker.
Three of those sentences are scar tissue. "Produce the plan only" stops the agent calling the deck builder and raising a second approval card for the same deck. "Do not state an approval id" exists because an earlier version of this prompt said report the approval id, and the agent dutifully invented one — it was the deck's filename. And the markers exist because a flow cannot reliably find JSON inside prose; give it two fences and the extraction is a one-line expression.
Instructions to append
When you are invoked by a process rather than by a person, nobody is present to
answer a follow-up question. So: never ask a clarifying question in that context.
If something is ambiguous, choose nothing, state the ambiguity in needs_review,
and let the approval step put it in front of a human.
What you should see
  • Nothing at all, for several minutes — which is the point. No window is open. No one is waiting.
  • Then an approval card in Teams, carrying the fund record and slide plan the agent built from a file you did nothing with except save it in the right place.
  • In the agent's reply, the ambiguity rule doing its job unprompted: with no client id supplied it does not ask who the client is — it puts client_mandate in needs_review, records that the mandate action was never called because nothing identified the client, and carries on.
  • A second entry in needs_review you did not plant: isin, because the factsheet prints INF000SAMPLE01 (illustrative) and the agent will not treat a qualified value as confirmed. Two fields, under the threshold, so the plan is still produced — which shows the counting rule working. The messy document cannot show that: there, everything fails at once.
  • With the messy document, the agent stops instead: more than three fields in needs_review, so it reports the failure rather than producing a confident, wrong deck. An agent that declines to run is a working agent.
  • Then nothing again, until you answer the card — the run stays open, and the run history shows the wait as a step with a duration. Hours are normal and correct.
  • Within about fifteen seconds of approving: a .pptx and a .pdf in OneDrive, both stamped with the same timestamp, and an email in your inbox with the PDF attached. On the verified run the deck landed 1 second after approval and the PDF 8 seconds after that.
  • Reject instead, and the opposite: no files, no client-facing anything, and an email telling you so. Both outcomes end in somebody being told, which is the difference between an unattended process and an unsupervised one.
  • In the flow's run history: the whole chain, timestamped, with inputs and outputs you can read back months later when somebody asks where a number came from — including who approved it and when.
When it does not behave
  • The trigger never fires. SharePoint and OneDrive triggers poll rather than push, and the wait is not consistent — the same flow has started in the same minute as the drop and, another time, a couple of minutes later. Check the flow's run history before you change anything; the most common "broken trigger" is an impatient builder.
  • You cannot find the action. Search the action list for copilot, not for agent: the connector is Microsoft Copilot Studio and the action is Execute Agent and wait (its siblings are Execute Agent and Evaluate Agent). If your tenant restricts it, run the same chain from a Scheduled trigger instead and demonstrate the identical point. Unattended is unattended, whatever started it.
  • You are tempted by plain Execute Agent, without the wait. Only the waiting version returns body/lastResponse — which is what puts the fund record, the enrichment table and the slide plan on the approval card. Drop the wait and the reviewer gets a card with nothing to review.
  • You expect this leg to time out too. It does not. The ~100-second ceiling that forced Create an approval in demo 2.6 applies to an agent calling a flow. This is the other direction — a flow calling an agent — and it happily ran for two and a half minutes. Worth saying out loud, because the two look symmetrical and are not.
  • It asks a clarifying question and then waits forever. Exactly the failure the appended instruction prevents. Add it, republish, and drop the file again.
  • Two approval cards arrive for one dropped file. Your agent still has a deck-building tool with its own approval gate and it called it anyway — so you have the flow's card and the tool's. Check the "produce the plan only" line is actually in the Message. Do not fix it by deleting the flow's approval: that hands the human gate back to the model, which is what step 5 exists to prevent. And if two similar cards are already queued, read the timestamps — approving the wrong one leaves the run waiting and looks exactly like a broken flow.
  • The expression editor rejects something that is obviously right. The designer accepts outputs('X')?['body/Name'] in some fields and outputs('X')['body']['Name'] in others, and it will not tell you which it wants. Both mean the same thing. Try the other bracket style before you assume the expression is wrong — it cost real time on the build.
  • The reply names an "approval reference id" that does not work. It is the deck's filename, and the reply claims the plan was "sent for approval" before the flow had created anything. The model is narrating a step it did not take — step 5's failure surviving in the prose even when the flow does the real work. Read it out; it argues for the deterministic gate better than any slide.
  • Everything is blocked in your tenant. Read the steps and watch the trainer. The architecture is the transferable part, and it is unchanged whichever button starts it.
Carry this forward

This is the shape to take to your platform team, because it is the shape that changes a working week. An agent in a chat window saves a person some typing; an agent on a trigger removes a step from the process and puts a human at the decision instead of the keyboard. When you map your own workflow — demo 1.7 — the steps worth automating first are the ones that begin with "when X arrives", because those already have a trigger waiting to be used.

Where the evidence lives — open these three once before you leave. The agent's Analytics tab: sessions, engagement, and the share of conversations that ended without an answer — a rising unanswered rate is your knowledge going stale, visible here long before anyone complains. Session transcripts, retained as Dataverse rows: the honest answer to “show me every question anyone asked this agent last quarter”, which run history cannot give you because most conversations never reach a flow — check the retention period your tenant applies, it is a setting and it needs an owner. Flow run history: elapsed time and outcome per unattended run, which is what turns the ROI estimate into a measurement. Screenshot the analytics page at week four; the case that gets a second agent funded is the one with actuals in it.

12. plan-to-pptx.py — plan in, PowerPoint out (demo 2.5)

The last hop, in one file. pip install python-pptx, then python3 plan-to-pptx.py slide-plan-sample.json deck.pptx. It writes a real, editable PowerPoint file — a native chart you can click into, a real table, every figure carrying its source, and a closing slide built from unresolved. No tenant, no connector, no licence. For a PDF afterwards: soffice --headless --convert-to pdf deck.pptx. Two details worth opening the code for. It shrinks type rather than let text overflow its box, because the library cannot compute autofit — that is the defect which finds every report generator the first time real commentary runs longer than the sample. And it refuses to print a source line it does not have, which is the schema's discipline carried one step further down the pipeline.

One failure from hosting it, worth more than the script. Behind an HTTP endpoint, the first call driven by the agent returned 500 with an empty body while the same code had just succeeded on the sample plan. The agent had titled the deck with an em-dash, the handler put that title into a Content-Disposition header, and HTTP headers are Latin-1 only — the response died before it was written. Every local test had passed, because every local test used the ASCII fixture. Test the last hop with the agent's own output, not with your sample file. Model output routinely carries em-dashes, curly quotes and non-breaking spaces; your fixture never does.

After the workshop — taking this into your own environment

Everything you built today lives in a training environment on synthetic data. Rebuilding it against your own systems is a separate piece of work with real dependencies. These are the six conversations to start, in this order:

  1. An environment. A Power Platform environment your team owns, with dev and prod separated. Ask for this first — everything else waits on it.
  2. Connector approval and DLP. The specific list of connectors your agent needs, and which data groups they sit in. This is the dependency with a queue in front of it, so start it early.
  3. An identity for the agent. How it authenticates to your internal and legacy systems — a service principal, a gateway, or an API wrapper around what exists.
  4. Data classification, not just DLP. DLP governs which connectors may combine; it says nothing about the sensitivity of what the agent reads and writes. Two questions for your information-protection owner: can a user be cited to a document they may not open (with user authentication, no — results trim to the asker), and does a generated deck inherit the label of its most restrictive source (no — it carries no label until something applies one). The second is the gap: decide who labels the output before the first client deck exists.
  5. A named owner and reviewer. Not a formality: an agent nobody owns stops being maintained within a quarter, and an approval gate with no time behind it is theatre.
  6. The publishing route. Teams you can usually reach yourself. Microsoft 365 Copilot goes through the organisation catalogue and an administrator's approval queue — so find out who holds that queue and what they need from you. Ask in week one; it is the request that decides your launch date, not your build.
Bring your workflow map from demo 1.7 to that conversation. A request framed as "we want to remove four steps from the quarterly review, here is the map and here is what it needs" lands very differently from "we would like to try Copilot Studio".

Three defects that will find you the first time you write to Dataverse

Nothing today writes to Dataverse — the capstone stages everything in SharePoint on purpose. In your own environment it will be a Dataverse table soon enough, and these three cost an afternoon each the first time:

What you seeWhat is actually wrong
A choice column rejects the write, or silently stores the wrong optionYour form or card collects the choice label as text ("High"); Dataverse stores the choice value as a number. Map it explicitly — set a variable with a Power Fx Switch(Topic.Priority, "Low", 1, "Medium", 2, "High", 3, "Critical", 4, 1) and write the variable, not the label.
The write errors on a field you have clearly mappedYou bound the whole record where the column wants a field. Pick the field explicitly — TicketTitle.Text, not TicketTitle. The designer reports this unhelpfully, so check every binding rather than hunting the message.
A lookup column will not accept anything you give itLookups want the OData form, not a name or a GUID on its own: /contacts(<guid>). Get the GUID with a List rows step filtered on emailaddress1 eq '<System.User.Email>', coerce it to text, then build the string. System.User.Email is also the cleanest hook for “who is asking” — the identity question from session 2.2, answered concretely.
