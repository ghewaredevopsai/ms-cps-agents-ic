What the model is actually doing when it answers1.1

Consequences you will design around

  • It is never silent. A confident number is the default output, whether or not the data exists.
  • Same question, different answer. Sampling is probabilistic — two runs can differ. That matters for anything repeated monthly.
  • It has no access to anything you did not put in the context. No NAV feed, no ledger, no internal system — unless an action fetches it.
  • Errors compound. A wrong figure in sentence one is treated as fact by sentence four.
The trap for a consulting team: the failure looks exactly like the success. Fluent, formatted, correctly-worded — and wrong.
So: the engineering task is never “make it smarter”. It is constrain what it can see, and check what it produces — which is what the rest of the day builds.

The three ways it breaks on consulting work1.1

Which one should worry you most

  • Not #1. A fabricated 3-year return is usually caught — a reviewer knows the factsheet.
  • #2 is the real risk. Gross-vs-net or wrong share class survives review because every number on the page is genuine.
  • #3 is not a model problem at all — it is an integration problem, and it is the one Copilot Studio actually solves.

The controls, previewed

  • Grounding → kills most of #1  (next slide)
  • Schema + validation → catches #2  (2.4)
  • Actions calling real systems → removes #3  (2.2, 2.3)
Rule we will apply all day: numbers come from systems, narrative comes from the model. Never the reverse.

Grounding — what it fixes, and what it does not1.1

What changes

  • The question stops being “what do you know?” and becomes “what does this document say?”
  • Citations make it reviewable. An unverifiable answer has no place in a client deliverable; a cited one can be spot-checked in seconds.
  • Retrieval quality now decides answer quality — a stale corpus produces confidently stale answers.

What you must add on top

  • Instructions that permit refusal — “if the figure is not in the source, say not stated.”
  • Computation in a tool, not the prompt — Excel or SQL does the maths (2.3).
  • Freshness discipline — who refreshes the corpus, and how often.
Grounding is the single highest-value control available to you today — and it needs no new licence, tooling or approval.

Setting the accuracy bar: not every output carries the same risk1.1

Why this ladder decides everything

  • Teams stall by applying client-deliverable standards to internal drafts — so nothing ever ships.
  • Or the reverse, which is worse: an AI-drafted paragraph reaches a trustee pack unreviewed.
  • Decide the tier before you build. The tier sets the controls, the review model, and whether the agent may act unattended.

The question to ask of any use case

  • Who sees the output — me, my team, or the client?
  • What happens if it is wrong and nobody notices?
  • Is there a human who would catch it, and do they have the time?
The capstone — the Investment Report Agent — sits at tier 3: it drafts the whole deck, a consultant signs it off, and only then does it go out.

Anatomy of a prompt that survives contact with real work1.2

Why this structure and not another

  • Each part removes one class of failure: role fixes tone and assumptions, context fixes fabrication, task fixes vagueness, format makes output machine-usable, example fixes ambiguity.
  • Drop any one and you can predict which failure returns.

Habits that pay off

  • Name the fields. “Key highlights” gets you a different set every run.
  • Always permit “not stated”. Silence must be a legal answer.
  • Ask for the source page. Free verification, and it discourages invention.
  • Keep the good ones. A prompt that works is a team asset, not a chat message.
These five parts do not disappear when you move to Copilot Studio — they become the agent's Instructions. You are already writing agent code.

Never ask for the whole report: decompose into model-sized steps1.2

The judgement being taught

  • Language in, language out → model. Reading a PDF, writing commentary.
  • Numbers, rules, files → tool. Arithmetic in Excel or SQL; the deck built by a template engine.
  • A single mega-prompt collapses all six steps and you cannot tell which one failed.

Why this is the map of Module 2

  • Step 2 → 2.4 extraction · step 3 → validation rules · step 4 → 2.3 Excel/SQL · step 5 → instructions · step 6 → 2.5 PowerPoint.
  • Today your developers do all six by hand, with Aspose and custom code carrying steps 4 and 6.
Decomposition is the skill. Once the six steps are separate, each one can be tested, fixed and automated independently — and only two of them need a model at all.

The prompting ceiling — and why your pilot hit it1.2

This is the hinge of the whole day

  • Copilot made individuals modestly faster. It could not enter the workflow, so the process kept its shape — and the process is where the time goes.
  • Governance and tooling limits get the blame, and they are real. But even with perfect access, prompting alone would still hit these four walls.

The definition we will use

An agent is what you get when you give the model three things it does not have on its own: knowledge it can always see, tools it can call, and a place to run where it can be shared and audited.
  • That is not a philosophical definition — it maps exactly onto the four things you configure in Copilot Studio. Next slide.

Chatbot → grounded assistant → agent: what actually changes1.3

Reading the table honestly

  • Most “AI rollouts” stop at column two — useful, popular, and invisible in process metrics.
  • Column three is where automation shows up in cycle time, because the agent does steps rather than advising a human who does them.

What column three costs you

  • Connections have to be approved. Actions have to be built. Failures need handling.
  • Somebody owns it — an agent is a small production system, not a chat.
  • That ownership is the price of the productivity, and it is worth naming up front.
Copilot Studio is where columns two and three are configured — the same tool, a different level of ambition.

How the agent decides what to do1.3

Two ways to drive the loop

  • Generative orchestration — the agent plans each request itself. Flexible, handles phrasing you never anticipated, occasionally surprises you.
  • Topics — you script the exact path for a named situation. Predictable, testable, rigid.
  • Use both. Generative for the open work; a topic for anything where the behaviour is non-negotiable — regulatory wording, escalation, refusals.

What makes this debuggable

  • The trace is the log: which action, what inputs, what came back, why it stopped.
  • Most fixes are a sentence in Instructions — not a rebuild.
You will watch this loop pick the wrong action this afternoon in 2.1 — and watch it get corrected in about ninety seconds.

Where Copilot ends and Copilot Studio begins1.3

Why the distinction is practical, not academic

  • It explains the pilot result precisely: Copilot was asked to do a job that needed the other column.
  • It is also a governance conversation. Copilot needed no new approvals. An agent that calls a legacy internal endpoint needs a connector, a service identity and a DLP decision — and that is a normal, answerable request.

Not a migration

  • They coexist. Copilot stays for individual drafting; agents take the repeatable pipeline work.
  • Your team keeps using Copilot for code review exactly as today — nothing here replaces it.
Same login, same tenant, same data boundary. Copilot Studio is not a new vendor decision — which is why it fits inside your current governance.

Honest limits: what Copilot Studio should not be asked to do1.3

Where it is genuinely strong

  • Document-shaped work, low-to-moderate volume, humans in the loop, Microsoft-centred data.
  • Time to first working agent: hours. That is the point — it makes the idea testable before anyone commits engineering.

Where it will fight you

  • Latency & throughput — conversational speed, not batch. Ten thousand documents overnight is the wrong shape.
  • Fine control — you steer orchestration with words, not code. Complex branching logic gets awkward fast.
  • Testing & ALM — regression testing is thin; dev→test→prod takes deliberate effort.
  • Deep custom logic — proprietary models, heavy computation, real-time pricing: not here.
Say this to your stakeholders: a fast, governed prototyping platform — and the honest place to prove value before asking for engineering budget.

Your workflow, marked up: where an agent belongs — and where it does not1.4

Why the Copilot pilot did not move the numbers1.4

The diagnosis

  • The pilot was not badly run and the team was not wrong about the tool. It was measured against pattern B while only pattern A was possible.
  • Pattern A gains are individual and hard to see in a process metric. They also do not compound.

What unlocks pattern B

  • Permission for the agent to call a system — the connector and DLP conversation.
  • An owner for the agent, and a place for it to run.
  • One approval gate the business trusts, so autonomy is bounded rather than debated.
This is the honest answer for your stakeholders: the pilot proved the model works. It could not prove the process changes — because nothing was allowed to touch the process.

Where the internal GPT tool sits, and what an agent adds1.4

Why the distinction is worth making internally

  • “We already have the GPT tool” is the most common reason an agent programme never starts. It is a category error — like saying you have a search engine, so you do not need a report.
  • An agent is narrow by design. Its value comes precisely from doing one job the same way every time.

Practical consequence

  • Keep the GPT tool for open questions across the firm.
  • Build agents where the work is repetitive, document-shaped and system-connected — the green column on the previous slide.
  • Neither requires the other to be replaced or defended.
If someone can describe the task as a procedure with a predictable output, it is an agent candidate. If they cannot, it is a chat question.

Picking the first agent: four criteria, one picture1.4

The four criteria, in priority order

  • 1  Repetition. If it happens twice a year, the build will never pay back. Frequency beats glamour.
  • 2  Data readiness. Does the input already exist in a form a system can reach? Unready data is the most common silent killer.
  • 3  Value. Hours saved × how many people × how often — state it as a number you would defend.
  • 4  Risk. Which tier from slide 6? Tier 4 is not a first agent.

Disqualifiers

  • No named owner · no reviewer with time · input arrives as email attachments nobody controls · the process itself is about to change.
Your reporting pipeline scores well on all four — which is why it is the capstone, and not simply because it is painful.

The governance envelope an agent lives inside1.4

Read it from the outside in

  • None of these layers is new. They already exist for Power Platform in your tenant — an agent inherits them rather than asking for an exception.
  • That is the single most useful thing to tell a governance forum: this is a configuration inside an approved boundary, not a new vendor or a new data path.

The four questions you will be asked

  • What data does it touch? → knowledge scope + connector list
  • Where does data go? → stays in tenant unless a connector says otherwise; that is what DLP governs
  • Who can use it? → sharing roles, environment membership
  • How do we know what it did? → the run trace and audit log
Have the connector conversation before you build, not after the demo. It is the one dependency that has a queue in front of it.

What we build after lunch — and what we need from you

Before we break: pick the one step of your own week you would hand to an agent first — and be ready to say why it beats the other candidates on repetition, data readiness, value and risk.
