Two ways to drive an agent — and when each is wrongPRE · DEMO 2.12.1

What generative actually costs you

  • Non-determinism. Two identical requests can take different routes. Acceptable for drafting, not for a compliance statement.
  • Description-driven routing. Your action descriptions become the control surface. A vague description is a bug.
  • Debugging shifts from "read the flowchart" to "read the trace".

The pattern we will build

  • Generative orchestration for the whole reporting pipeline.
  • Topics for exactly three things: the advice refusal, the disclaimer wording, and escalation when a mandate breach is detected.
Those three topics are not a limitation of the tool — they are the places where you have decided, deliberately, that the agent gets no discretion.

Instructions are production code — annotatedPRE · DEMO 2.12.1

Read it as a defect list

  • Lines 1–2 → fabrication. The rule that turns recall into reading.
  • Citation line → makes every claim checkable in seconds, which is what lets a reviewer accept it at all.
  • “not stated” → silence becomes a legal answer. Without this the model always fills the gap.
  • The arithmetic pair → totals, averages and conversions move to Excel and SQL in 2.3; a difference between two figures already on screen may be stated, because a reader can check it by eye. Session 2.3 draws that line properly.
  • Ambiguity rule → the gross-vs-net failure. The one that survives review.
  • Failure rule → an action that times out must not become an invented number. This is the line teams forget.

Treat it like code

  • Version it. Review changes. Never edit the published agent directly.
  • When behaviour changes unexpectedly, diff the instructions first — it is nearly always the last edit.
You are not writing a prompt. You are writing the specification that a non-deterministic component is held to — which is why it belongs in source control, not in a text box someone edits on a Friday.

Reading the trace: where the ninety-second fix comes fromPRE · DEMO 2.12.1

The debugging discipline

  • Isolate before you accuse. Test the flow standalone in Power Automate first. Half of all “agent bugs” are flow bugs.
  • Wrong action chosen is the most common failure by a wide margin — and it is always fixed in the description, never in the logic.
  • Right action, wrong input → the parameter description is doing no work. Add an example value to it.

What to log for the auditors

  • Run id, user, timestamp, every action called with inputs and outputs, the citations returned, and the approval decision.
  • That list is not a nice-to-have — it is the answer to “how do we know what it did?”, and you will be asked.
If you take one habit from this afternoon: read the trace before you change anything. It converts a guess into a diagnosis.

Proving a change helped — test sets, not impressionsPRE · DEMO 2.12.1

Why your three favourite questions are not a test

  • You edit one instruction, re-ask the questions you always ask, and the answers look better. That is an impression, not evidence — the same question can pass on Tuesday and fail on Wednesday.
  • None of this is deterministic, so a single pass proves nothing. Only a fixed set of questions holds still while the agent changes.

What a test set actually is

  • A stored collection of single questions, or whole conversations, each with the answer you expect. Run it, score it, change one thing, run the identical set again, compare.
  • Copilot Studio will generate the first set from the agent's own description, instructions and knowledge — so it costs minutes, not a morning.
This is what turns “it feels better” into a number you can put in front of a governance forum. Sometimes that number says the change earned nothing — which is the most useful answer it gives, and the one no amount of watching the chat window would have produced.

The loop you will use for the rest of the afternoonPOST · DEMO 2.12.1

Read the trace before you change anything, and change one thing at a time. A fix you cannot attribute is not a fix you can defend when somebody asks next month why the agent behaves differently.

Four ways to give an agent hands — pick deliberatelyPRE · DEMO 2.22.2

How to choose in one minute

  • Does a connector already exist? Use it. Reaching past a governed connector to hand-roll HTTP is how agents fail review.
  • One call, one agent, some shaping? Flow.
  • Your API, several agents, real contract? Custom connector — and now you need the OpenAPI spec, which is often the real blocker.

The question that saves a month

  • Does the endpoint already exist and is it documented? If no, you are not building an agent this quarter — you are building an API, and that is a different project with a different team.
For the capstone we use route 1 for Excel, route 2 for both APIs, and we will name exactly where route 3 takes over in your own environment.

Step 2 is the whole game. The agent routes on your action description — so write it as a sentence that says when to use the tool, not what the endpoint is called.

Reaching an internal or legacy system — three honest patternsPRE · DEMO 2.22.2

Why this matters more than the tooling

  • Which pattern you are in decides your timeline far more than anything in Copilot Studio does.
  • Find out before you promise a date. One conversation with the system owner beats three weeks of optimism.

Ask the system owner four things

  • Is there an HTTP endpoint, and is it documented?
  • How does a service authenticate — not how a person does?
  • What is the rate limit, and what happens when we exceed it?
  • Is the data classified in a way that changes who may read it?
The trap: a successful demo against a mock, followed by six months of discovering the real system is pattern C. Do the discovery first — it costs an afternoon.

Who is the agent when it calls your system?POST · DEMO 2.22.2

The two models, and the choice

  • On-behalf-of the user. The call carries the signed-in consultant's permissions. If they cannot see the client, neither can the agent. Safest default for anything client-scoped.
  • A service identity. The agent has its own account with its own rights. Predictable and shareable — and, if scoped lazily, a standing key to everything.

Getting this wrong looks like

  • An agent shared with the team that quietly reads every client's mandate, because it runs as a service account with blanket access.
  • No one notices, because every individual answer looks correct.

Decide per action, not per agent

  • Client-scoped reads → on-behalf-of.
  • Reference data everyone may see → service identity.
  • Writes → service identity, narrowly scoped, always logged with the requesting user.
  • And one switch above all three: Settings → Security → Authentication. “Authenticate with Microsoft” is what makes knowledge results trim to each asker's own permissions. Leave it off and everyone sees one index — check it before you share the agent.

Failure engineering — the part that separates a demo from a systemPOST · DEMO 2.22.2

Where each control lives

  • In the flow: retry policy, timeout, Configure run after, and a condition that checks for empty before responding.
  • In the instructions: what to say and what never to substitute.
  • In the output contract: the unresolved list, so partial data cannot masquerade as complete.

Test it deliberately

  • Point one action at a URL that does not exist. Watch what the agent says.
  • Return an empty array on purpose. Watch whether “no holdings” becomes “0%”.
  • If you have not seen your agent fail, you do not know what it does when it fails.
In regulated reporting, a refusal is cheap and a confident wrong number is not. Engineer for that asymmetry.

The numbers boundary: where the model stops and a system startsPRE · DEMO 2.32.3

The instruction that enforces it

Never calculate a total, a weighted figure or an average yourself, and never convert a currency yourself. Retrieve the number using an action and quote it. You may still state the difference between two figures you have retrieved, as long as both are shown with their sources. If a calculation is needed and no action provides it, say which action is missing, and do not answer with a number.

Why the last clause matters

  • It converts a silent invention into a design task with a name: “I need an action that computes attribution.”
  • Your backlog of actions writes itself, from the agent's own complaints.

The test you can run today

  • Ask your agent for a computed figure, then ask: “which action produced that number?”
  • If it cannot name one, it did the maths itself — and you have just found a defect that no test suite would have caught.

Reading real data: Excel and SQL, without surprisesPRE · DEMO 2.32.3

Why shaping matters more than you expect

  • Everything you return becomes context the agent must reason over. Two hundred rows costs tokens, latency and accuracy at once.
  • Do the filtering where filtering is cheap — in the query or the flow, not in the model.

The two failures you will actually hit

  • Not a Table. The connector cannot see a plain range. Ctrl+T, every time.
  • Wrong OneDrive. Excel Online (Business) reads OneDrive for Business and SharePoint — not personal OneDrive.
Once numbers arrive from a system, the whole agent changes character: it stops being a document reader and starts being a participant in your data.

Writing back to a system of record — safelyPOST · DEMO 2.32.3

Reads and writes are not the same risk

  • A bad read produces a bad answer someone can catch. A bad write produces a bad record that outlives the conversation.
  • Retries are automatic in Power Automate — which is exactly why idempotency is not optional.

Where the capstone writes

  • The slide plan and the finished deck to SharePoint — a staging area, versioned, reversible.
  • Nothing touches a system of record until the approval gate has fired, and the approval id is stamped on the record.

Collecting the payload, not parsing it

  • An adaptive card asks for the fields the write needs — client, quarter, priority — as typed inputs. Each input becomes a variable you can bind straight to the write.
  • The same card renders in Teams, web chat and M365 Copilot. A typed field cannot be misread; a sentence can.
A useful test for any proposed write: if this ran twice by accident, what would we have to explain?

Extraction is hard for one reason: everything variesPRE · DEMO 2.42.4

The reframe

  • Extraction is not “can it read the document” — it can. It is “can I trust the output shape enough to build on it”.
  • That is a contract problem, and contracts are things you design, not things you hope for.

Three outcomes, not two

  • Found — the value, plus where it came from.
  • Absent — not stated, explicitly.
  • Ambiguous — found more than one candidate, or the label did not match cleanly. This third outcome is the one everyone forgets, and it is where the review time actually goes.
Design for all three and the downstream steps become simple. Design for two and you have built a system that lies by omission.

The schema is the contract the rest of the pipeline relies onPRE · DEMO 2.42.4

The four rules that make it a contract

  • Fixed key set. Never add, rename, drop or reorder. Downstream code depends on it, and a helpful extra key is a breaking change.
  • Absence is a value, not a missing key. not stated is data.
  • Provenance travels with the record — which document, which run.
  • Ambiguity is enumerated in needs_review, so the reviewer knows precisely where to look.

What this unlocks

  • The deck builder can be dumb, because the record is reliable.
  • Review shrinks from “check everything” to “check the flagged fields” — which is where the four hours actually go.
Notice "currency" carries a value and a flag. The factsheet prints Rs throughout but never the code INR — so reading it off the rupee is a reasonable inference, and listing the key in needs_review is what makes that inference visible to the next reader.

The validation ladder — four rungs, cheapest firstPOST · DEMO 2.42.4

Run them in this order

  • Each rung is cheaper than the one above and catches a different class of error. Skipping rung 1 to build rung 4 is the classic mistake.
  • Rungs 1–3 run in the flow, deterministically. Only rung 4 needs judgement — and even then, the agent flags rather than decides.

What each rung actually caught, in real pipelines

  • 1 — a return arriving as "n/a" where a number was expected.
  • 2 — a 156% allocation, from a mis-read table.
  • 3 — allocations summing to 103% across four sleeves.
  • 4 — a fund beating its benchmark by 40 points, because a gross figure met a net benchmark.
Every one of those would have looked plausible on a slide. That is the point of the ladder.

Never let the agent build the deck. Let it write the plan.PRE · DEMO 2.52.5

Two constraints that carry the quality

  • Every figure carries a source string. If it cannot be sourced, it cannot go on a slide — it goes to unresolved.
  • Commentary may only reference figures already on a slide. This one rule stops the classic failure: a narrative paragraph containing a number that appears nowhere else in the deck.

What the reviewer now does

  • Reads the unresolved list first — that is the whole job.
  • Spot-checks two sourced figures against the citation.
  • Approves. Minutes, not hours, because the plan is honest about what it does not know.
This is an ordinary engineering idea — an intermediate representation with a contract — applied to a place your team has not applied it yet.

Turning the plan into a deck: four options, honestly comparedPOST · DEMO 2.52.5

Why option A wins for you specifically

  • Your Aspose code encodes years of house-format decisions. That is an asset, not legacy.
  • Nothing new to license, nothing new to procure, no new data path to defend in a DLP review.
  • The wrapper is a normal internal API — the same conversation as pattern A in session 2.2.
  • If the licence is the objection, python-pptx writes the same file from the same plan. The architecture does not move — only what sits behind the endpoint.

What changes for your developers

  • They stop running the generator and start maintaining it as a service.
  • The interesting work moves up: the schema, the validation rules, the sourcing discipline.
  • They test it with the agent's output, not with a fixture. The first live call to a hosted renderer failed on an em-dash in the deck title — every local test had passed on ASCII.
Today you see it both ways: plan-to-pptx.py run locally — one library, no licence, no tenant — and the same script hosted behind an endpoint the flow calls, so the chain completes with nobody at the keyboard. In your environment, that box is already built.

What stays in code — and shouldPOST · DEMO 2.52.5

The line, stated once

If it has one correct answer and always did, it stays in code. If it needed a person to read something and decide, it is a candidate for the agent.

The failure mode after a good demo

  • Someone proposes moving the calculation engine into Copilot Studio because “it worked for the factsheet”.
  • Six weeks later there is a slower, less accurate, less auditable version of something that already worked.
  • The demo does not tell you where the boundary is. This slide does.

A healthy end state

  • Agents read, decide, orchestrate and explain.
  • Code computes, renders and integrates.
  • Humans judge, approve and own.

Publishing: what actually happens, and where people meet itPRE · DEMO 2.62.6

The publish checklist

  • Tested in a fresh conversation, not the one you were editing in.
  • Every action tested against a real failure, not just a happy path.
  • You know the rollback: which version, and who can trigger it.
  • Someone other than you has used it and not been confused.

Sharing is a governance decision

  • Users can run it. Co-authors can change it. Those are different risks — and co-authoring an agent that calls a legacy system is a privileged action.
  • Share to a group, not to individuals, or maintenance becomes a leaver-process problem.
Reaching M365 Copilot is not a toggle you own: publish, choose the audience, then submit to the org catalogue — where an administrator approves it, sets who may install it and applies the tenant policy templates. Raise that request in week one, not the week you want to launch.

Environments and ALM: the part that decides whether this survivesPRE · DEMO 2.62.6

Three rules, learned expensively

  • Never build in the default environment. It is shared with the entire tenant, it cannot be governed properly, and moving out later is a rebuild.
  • Put the agent in a solution from day one. A solution is what makes it exportable, importable and versionable.
  • Use connection references, not embedded connections — otherwise the agent carries your credentials to production, which is both a security finding and a single point of failure when you take leave.

What DLP actually does here

  • Connectors sit in business, non-business or blocked groups, and a flow may not combine across groups.
  • That is the mechanism your governance forum will use to say yes — so bring them the connector list, not a description of the idea.
The gap between a working demo and a supported service is almost entirely this slide. It is also the least glamorous and most predictive.

The approval gate is where autonomy is actually setPRE · DEMO 2.62.6

Autonomy is a dial, not a switch

  • Draft freely — the agent may read, extract, enrich and compose without asking.
  • Gate the irreversible — anything that leaves the firm, writes to a system of record, or is described as final.
  • That split, written down, is your autonomy policy. It is more concrete and more useful than any statement of principles.

Why the unresolved list belongs on the card

  • It gives the approver something specific to do, which is the difference between review and ritual.
  • It also creates the feedback loop: repeated flags on the same field tell you which action to build next.

When to graduate — and how you will know2.7

The trap in both directions

  • Too early — you spend six months building infrastructure for a use case nobody has validated. The most expensive way to be right.
  • Too late — you accumulate fifteen agents nobody can test, in an environment nobody owns, and the eventual migration is a rewrite.

The healthy pattern

  • Prototype in Copilot Studio. Always. Even if you know it will end up in code — you learn the real requirements in a fortnight rather than a quarter.
  • Graduate individual agents when they earn it, on the five signals. Not the whole portfolio, and not on principle.
Today's decision is not Copilot Studio versus Agent Framework. It is whether the reporting pipeline is worth automating at all — and you now have enough evidence to answer that.

The ROI case, in numbers your sponsor will accept2.7

Build it conservatively, on purpose

  • Claim time to first draft, not total elimination. The review does not disappear — it shrinks and moves.
  • Count the build cost honestly, including the connector approvals and the Aspose wrapper. A case that survives scrutiny beats one that impresses.
  • Name the second-order benefits separately, and do not put a number on them: traceability, consistency between consultants, and a faster path from data to a client conversation.

The sentence that gets funded

“We remove four of the six steps in the quarterly review, keep the Aspose generator, add one approval gate, and every figure becomes traceable. Payback inside two quarters on time saved alone.”

What will be challenged

  • “What if it is wrong?” → the gate, the unresolved list, the audit trail.
  • “Who maintains it?” → the named owner. Have the name ready before the meeting.
  • “How do you know anyone uses it?” → the Analytics tab, at the second meeting. Estimates get you funded once; actuals get you funded again.
