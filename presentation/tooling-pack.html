Tooling Pack

Copilot Studio from the Command Line — with GitHub Copilot CLI
Take away from 27 August 2026 | Eight parts | For the developer track | Trainer: Rajesh Gheware
What this is. Everything demonstrated on the day was clicked — the maker portal, a browser, a human driving each step. That is the right way to learn the product and the wrong way to run it once more than one person depends on it. This pack is the other route: the same agent as files on disk, driven from a terminal, with GitHub Copilot CLI as the agent that does the driving. Everything here is Microsoft tooling and works against your own environment.
Read this before you start clicking things in a terminal. The portal is still the place to learn an agent and the fastest place to try one idea. Command-line tooling earns its keep at the point where you need three things the portal cannot give you: a reviewable diff of what changed, a repeatable deployment into a second environment, and a way to notice that someone edited production last Thursday. If none of those three is a problem for you yet, bookmark this and carry on clicking — you are not missing anything.

1 · The tools — what each one is actually for

Six command-line tools matter here. They are not alternatives to each other; each owns a different part of the picture, and the common mistake is reaching for the wrong one and concluding the job is impossible.

Tool Install What it does for a Copilot Studio agent When you need it
GitHub Copilot CLI
copilot		 npm i -g @github/copilot The agent that drives everything else. Reads and writes files, runs commands with your approval, and loads MCP servers as extra tools. Always. This is the thing you talk to; the rest are what it calls.
Power Platform CLI
pac		 dotnet tool install --global Microsoft.PowerApps.CLI.Tool The only programmatic surface for a Copilot Studio agent. Clone it to disk, push changes back, pack it into a solution, export and import. Any time the agent definition itself is the thing you are changing.
CLI for Microsoft 365
m365		 npm i -g @pnp/cli-microsoft365 Inventory and surroundings — list every agent in an environment, list and export solutions, upload a file into the SharePoint library your agent reads from. Auditing what exists, and moving the data an agent works on.
Azure CLI
az		 Your platform's package manager, or pip install azure-cli Everything behind a custom action — the resource group, the function app, the app registration an unattended caller signs in with. Only if your agent calls an endpoint you own.
Azure Functions Core Tools
func		 npm i -g azure-functions-core-tools@4 Run that endpoint on your laptop before it exists in the cloud, then publish it. Same condition as az, one layer up.
Git
git, gh		 Almost certainly already installed Where the cloned agent lives once it is files. This is the whole point of the exercise. Always.
The one-line summary if you remember nothing else. pac is for the agent, m365 is for everything around it, az is for what it calls, and Copilot CLI is what saves you from having to remember any of their syntax. You describe the outcome; it assembles the commands and shows them to you before running them.

Why GitHub Copilot CLI rather than just typing the commands

Because the syntax is the least interesting part of the job and the easiest to get wrong. The commands in this pack have awkward edges — an identifier that means two different things in two different APIs, a subcommand that silently does nothing without a sibling directory, a flag whose absence changes the result rather than producing an error. An agent that can read the error, re-read the file it just wrote, and try the other form is worth more than a memorised cheat-sheet. Your part is to know what should happen, which is what the rest of this pack is for.

Approval, not autonomy. Copilot CLI asks before it runs a command that changes anything. Keep it that way while you are learning the surface — the useful failures in Part 4 are ones you want to see, not ones you want quietly retried five times.

2 · MCP, the other way round

You met MCP on the day as something a Copilot Studio agent consumes: a server exposes tools, and your agent calls them. Here it is inverted. The terminal agent is the consumer, and MCP servers are how it reaches Azure, Microsoft 365 and GitHub without you pasting output between windows.

MCP server What it gives Copilot CLI Worth adding?
Azure MCP Server
@azure/mcp		 Subscriptions, resource groups, storage, Key Vault, monitoring and log queries — plus a passthrough for anything it does not model directly. Yes, if your agent calls an endpoint you host.
Microsoft 365 / Graph Mail, SharePoint, OneDrive, Teams, Excel — the systems your agent's knowledge and actions actually touch. Yes. Most useful for staging the documents a demo depends on.
GitHub Repositories, pull requests, issues. Yes, once the agent definition is in source control — which is Part 6.

Configuration is a JSON file listing servers and how to start each one. The exact path is a Copilot CLI setting rather than something to memorise — ask it: "where is your MCP configuration file, and what servers are loaded right now?"

{
  "mcpServers": {
    "azure": {
      "command": "npx",
      "args": ["-y", "@azure/mcp@latest", "server", "start"]
    }
  }
}
There is no Copilot Studio authoring MCP server, and you should not wait for one. Copilot Studio exposes nothing for an outside agent to author against — it is an MCP client, not an MCP server. Anything that changes an agent definition goes through pac. If a terminal agent ever tells you it has connected to Copilot Studio directly, it has misunderstood the question; check what it actually ran.
An MCP server inherits your permissions, not more. It signs in as you and can do what you can do. That is a reason to be careful, not a reason to be relaxed: a terminal agent with the Microsoft 365 server loaded can read every document you can read. Everything the day said about sensitivity labels and source permissions applies here unchanged — and, as on the day, nothing it generates inherits a label.

3 · The agent as files

This is the idea that makes the rest possible, and it surprises people: a Copilot Studio agent can be cloned to a directory, edited as text, and pushed back. Source control is not something you graduate to after leaving Copilot Studio. It is available on day one.

pac auth create
pac copilot list
pac copilot clone --environment <your-environment-id> --bot-id <agent-id>

What lands on disk:

PathWhat it holds
agent.mcs.yml The agent itself — its name, its description, its model hint, and the web-browsing capability flag.
settings.mcs.yml The switches, including the one that decides whether the agent may answer from the model when your knowledge does not cover the question.
topics/ One file per topic — the fixed-wording refusal you authored is a file you can diff.
knowledge/ The sources, including which one is marked authoritative.
actions/, workflows/ The tools and the flows behind them.
The two switches from the day live in these files. Allow ungrounded responses and Use information from the Web — the pair that decides whether your agent says "not stated" or invents a plausible number — are fields in settings.mcs.yml and agent.mcs.yml. Which means the most consequential governance decision in the whole product is reviewable in a pull request rather than a checkbox someone flipped and nobody noticed. Marking a knowledge source official is likewise a field, not a click.
Ask Copilot CLI to explain the diff, not just produce it. A useful prompt after any clone: "compare this against the last committed version and tell me, in plain English, what would behave differently for someone asking the agent a question." That is the review question. A raw YAML diff answers a different and less useful one.

4 · What pac can and cannot do

Four facts, each of which costs an hour to discover and ten seconds to read. They are the difference between "this tooling is broken" and "I was holding it wrong".

Fact 1 the one that wastes the most time create

pac copilot push cannot create an agent. It only updates one that already exists, because it needs the sync state that clone writes. Scaffolding a directory and pushing it fails with a complaint about no synced workspace — which reads like a bug and is not one.

If you want an agent to exist because a file says it should, the path runs through a solution import, not through push. Ask Copilot CLI for the sequence rather than memorising it; the point to carry is that create and update are different operations.

Fact 2 silent, and therefore nasty packaging

pac copilot pack rejects any directory it does not recognise. It accepts the agent and settings files, topics/ and the icon. Anything else — including directories it created itself on the way in, and including one you invent with a harmless name — makes it refuse.

The practical consequence: pack from a filtered copy, not from your working directory. This is exactly the kind of chore to hand to Copilot CLI, which will not forget the filtering step the second time.

Fact 3 the one identifier that lies identity

A flow has two different ids. The one the Power Automate API knows it by is not the one the underlying data platform knows it by. Adding a flow to a solution with the wrong one fails with "because it does not exist", which is true and unhelpful.

Whenever a command insists something does not exist and you can see it on screen, suspect the identifier before you suspect the tool.

Fact 4 useful, with two caveats cloning

There is a template extract-and-create pair that copies an agent wholesale — instructions, topics, tools, knowledge references — which is the fastest way to stand up a second copy for experiments.

Two things it does not do: knowledge sources come across as references without their bytes, so files still need uploading; and any literal braces in your instructions come back doubled, because the template format uses them for substitution. If a carefully-written schema arrives mangled, that is why.

5 · Testing — proving a change helped

The Evaluation tab and its test sets were the answer on the day: a fixed set of questions, one change per run, re-run the same set. Nothing about moving to a terminal changes that discipline — it makes it cheaper to keep.

The comparison the portal cannot give you

Once an agent is files, "did my change do what I intended?" has a second, sharper answer alongside the test-set score: clone the agent again and diff it against the version you started from. The score tells you whether behaviour improved. The diff tells you what actually changed — including the changes you did not intend.

Some portal actions change more than one thing. Marking a knowledge source as official also rewrites the agent's instructions. If you are holding yourself to one change per evaluation run, that is two — and the second one is invisible unless you diff. This is the single best argument for keeping a cloned copy alongside your portal session.

A baseline worth keeping

Clone the agent at a moment you are happy with, commit it, and call that the baseline. Then a rebuild — yours or a colleague's, in a workshop or in anger — can be scored against it rather than judged by eye:

  1. Clone the agent you want to check into a scratch directory.
  2. Ask Copilot CLI to compare it against the baseline and report differences by category — instructions, knowledge sources (including which is official), tools, topics.
  3. Read the categories, not the raw diff. "Two tools missing, refusal topic absent" is a finding; forty lines of reordered YAML is not.
Expect a good baseline to report differences that are not faults. If your baseline is an agent as it stood at the end of a build, anything compared against it mid-build will legitimately be missing the later pieces. A comparison is a prompt for judgement, not a pass mark.
The 30-second test that needs no tooling at all. It is still the best one, and it is in the reference pack: ask any new agent for three fields your source genuinely does not contain. An agent that answers all three is not ready, whatever its evaluation score says.

6 · Shipping and drift

Solutions are the unit that moves

An agent, its flows and its variables travel between environments as a solution — exported from one, imported into the next. Exported solutions are zip files, which diff about as well as any other zip file; unpack them and the contents become reviewable text. That single step is what turns "we deployed something" into "here is what changed".

Configuration that differs per environment

Anything that changes between development and production — an endpoint address, a key — belongs in an environment variable rather than pasted into two flows.

An environment variable is not a secret store, and this catches people out. The designer stamps the variable's current value into the flow definition when you save it. The action's header looks clean; the definition still carries the literal. What you have gained is one owned place to rotate the value instead of two pasted copies — which is worth having, and is not secrecy. If the value is genuinely a secret, it needs a Key Vault-backed variable, and your exported files still need checking before they go anywhere.

Noticing that someone edited production

Nothing stops a colleague opening the maker portal and changing an instruction. The fix is not a process document; it is a script you can run in ten seconds:

  1. Pull each tracked agent, export the solution, unpack it.
  2. Scrub anything that came back as a literal secret, replacing it with a placeholder.
  3. If git diff is empty, there was no drift. If it is not, that diff is the drift — commit it, and now you know.
Step 2 is not optional, and it is the step people skip. A pull faithfully restores real values over your placeholders — that is what "pull" means. Run the scrub every time, before git add, and never in the other order. A leaked key in a commit is not fixed by a later commit that removes it.
Run it after any portal session, and once after any delivery or workshop. Drift is not usually sabotage — it is a demo that got fixed live, a switch flipped to make something work, and nobody remembering a week later. Ten seconds of pulling beats an afternoon of "it used to work".

7 · The things that will stop you

Setup problems, in the order you are likely to hit them. None is a fault in your environment; all are worth recognising rather than debugging from scratch.

SymptomWhat is actually happeningWhat to do
m365 asks for an appId and will not log in Recent versions ship no default app registration. There is nothing to authenticate against until you register one. Register a single-tenant public-client app, declare the permissions you need, sign in against it. Ask Copilot CLI to build the command; this is exactly the fiddly-syntax case.
A command fails saying nobody has consented, even though you just signed in Interactive sign-in consents only the resource it needs at that moment. Permissions you declared but never exercised are still ungranted. Grant them once, deliberately, rather than expecting the login to cover everything. Verify against the actual grants, not the app's declared list — the declaration is intent, the grant is fact.
A whole consent operation fails because of one permission You have declared a resource that is not provisioned in your directory. Consent is all-or-nothing. Remove that resource and re-run. Leaving it in place breaks every future consent on that app, including unrelated ones you add later.
Commands that sound like they cover one product ask for a different one Tool names are marketing; the token a command requests is engineering. Some commands named after one service authenticate against a quite different resource. Do not assume a name tells you the permission. If it fails, look at what it requested, and be prepared for the honest answer to be that this command cannot work in your directory.
A globally-installed CLI is "not found" Its install directory is not on your PATH. Separately, a non-interactive shell does not read your shell profile at all. Add it to your profile for interactive use, and call tools by full path in scripts.
Never run these tools with a debug flag on a shared screen. Verbose debug output on some CLIs includes the raw authentication token exchanged with the sign-in service. That token is usable by anyone who reads it — off a projector, out of a recording, or out of a pasted log. Use the ordinary verbose flag, which tells you what you need without the credential.
A note on permissions you grant to a CLI. Some of the permission sets these tools recommend are broad — full control of every site, directory access as yourself. They are bounded by what your own account can already do, so they grant no new reach; what they change is how easily that reach can be exercised by something running on your laptop. Declare what you actually use, and add rather than starting wide. Your platform team will ask, and "I declared six permissions and here is what each is for" is a much better answer than "I accepted the defaults".

8 · A worked loop

Prompts, not commands — because the commands are the part you should be delegating. Each of these is a real request to make of Copilot CLI in a terminal open at your working directory. Read what it proposes before approving it; that reading is the learning.

Getting oriented
List every Copilot Studio agent in my environment with its
creation date and whether it has been published, then tell
me which ones look like abandoned experiments.
Putting an agent under source control
Clone the agent called "<name>" into ./agents/<name>/,
initialise a git repo if there isn't one, and commit it.
Before committing, check nothing in the files is a real
key or endpoint I would not want in a repository.
Reviewing a change someone else made
Pull the latest version of the agent in ./agents/<name>/
and compare it to the last commit. Explain in plain English
what would behave differently for someone asking it a
question, and flag anything that changes what it is allowed
to answer without grounding.
Preparing a demo's data
Upload ./samples/<file> into the SharePoint library at
<url>, then confirm it is there and tell me when the
agent's knowledge index is likely to have picked it up.
The end-of-week check
Pull every agent under ./agents/, export the solution,
unpack it, replace any literal keys with placeholders, and
show me a summary of what changed since last week. Do not
commit anything until I have read it.
Note the shape of the last one. It ends with do not commit until I have read it. A terminal agent is good at the six mechanical steps and has no opinion about whether the seventh should happen. Keeping the decision on your side of the line costs one clause.

Where this stops

None of this changes what an agent can do — the limits from the morning still hold, the numbers boundary still holds, and a governance checklist is still something a person fills in. What it changes is the engineering around the agent: reviewable, repeatable, and hard to lose. That is worth a lot on the second agent and almost nothing on the first, which is the honest reason this pack is a take-away rather than a session.
