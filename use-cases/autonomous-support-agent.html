Autonomous Support Agent

Build it yourself — Microsoft Copilot Studio
~35 minutes | No code | 3 connector tools · 1 event trigger | Trainer: Rajesh Gheware
Use a test mailbox and synthetic tickets. This agent reads mail and sends mail on its own, choosing the recipient itself. Build it against a mailbox you do not mind it replying from, and a project whose tickets contain nothing confidential. Do not point it at a shared or team inbox until you have worked through Before you use this for real at the end.

What you are building

An agent nobody talks to. A support request arrives by email. The agent wakes up on its own, reads the request, looks the ticket up in Jira, and replies — or says clearly that it found nothing. No chat window, no person in the loop.

Everything else you will build in Copilot Studio starts because a human typed something. This one starts because an event happened. That is the difference between an agent that sits beside your process and one that sits inside it.

It is also the shortest route to seeing a connector used directly as a tool — no cloud flow written by you in between.

Self-contained, and deliberately using none of the Northwind figures — nothing you build here can be mistaken for a demo value. The demos are in demo-guide.html.

Before you start

  • Copilot Studio, in an environment you are allowed to build in — not your organisation's Default environment if you can avoid it.
  • A mailbox you can send test mail to, and a second address to send it from.
  • A Jira Cloud site with at least one issue, and the issue key to hand (for example ABC-1).
  • Permission to create connections for Office 365 Outlook and Jira. The Jira connector is a premium connector — availability varies by licence, and that is a question for your admin rather than a blocker to reading on.
No knowledge sources are needed. This agent answers from a live system, not from documents — which is exactly why its tool descriptions matter so much.
Stage 1 Create the agent~5 min
  1. In Copilot Studio, choose Create → New agent, then Skip to configure so you land on the settings page rather than the description chat.
  2. Name it Autonomous Support Agent.
  3. Set the description — this is what other agents and makers see, so say what it is for, not how it works: 
    This agent provides responses to the support related queries received via email by looking up resources like Jira.
  4. Paste the Instructions. These are the whole brain of this agent — there is no knowledge source and there are no custom topics, so every rule it follows is in this box: 
    You are a Support Assistant. You would get queries via email having "Support" keyword contained in the subject. You would then use the connectors like Jira to get info regarding that ticket and respond appropriate to that email. If no relevant information found from the support ticket portals like Jira - then clearly respond saying "No information found for your query" but do not manufacture any facts.

Your communication should be polite, professional and concise.
  5. Click Create, then Publish once so the agent exists in a state a trigger can call.
Read the second sentence of those instructions again. "Do not manufacture any facts" is the only thing standing between a missing ticket and an invented one. It is a request, not a control. Stage 5 shows you how to test whether it is actually being honoured.
Stage 2 Add the Jira tool~8 min
  1. Open Tools → Add a tool → Connector and search for Jira.
  2. Choose Get issue by key (V2) and add it. Create or pick a Jira connection when prompted.
  3. Open the tool and set its inputs. This is the step people skip, and it is the one that decides whether the agent works:
    InputSet it toWhy
    Jira instanceA fixed value — pick your site from the listThere is exactly one right answer and it never changes. Anything you can pin, pin.
    Issue keyFilled by the model (dynamically)It comes out of the email, so only the model can supply it.
  4. Give the tool a description. The agent reads this to decide when to call it, so write it for the agent, not for a colleague: 
    This tool can be used to fetch Jira issue using issue KEY
The rule worth taking away: every input is either fixed by you or invented by the model. There is no third option. Anything that has one correct value should never be left to the model — and this agent has three more such inputs coming in Stage 3.
Stage 3 Add the mail tool~5 min
  1. Tools → Add a tool → Connector, search Office 365 Outlook, add Send an email (V2).
  2. Describe it in terms of the job, not the mechanism — this is what makes the agent reach for it after a Jira lookup rather than just printing an answer into the void: 
    Support queries received over an email should be responded via email and this tool is meant for responding to support queries.
  3. Publish the agent again.
Optional, and worth skipping the first time: Get emails (V3) can be added the same way. The reference build has it, but the triggering message is already handed to the agent in Stage 4 — so the tool is redundant, and it lets the agent read other mail in the folder. Add it only if you want to watch orchestration choose between two plausible tools.
Stage 4 Make it autonomous~8 min

Everything so far is an ordinary agent. This stage is the one that matters.

  1. On the agent's Overview page find Triggers, and choose Add a trigger.
  2. Pick When a new email arrives (V3). Confirm the Office 365 Outlook connection.
  3. Set the trigger's conditions:
    FieldValue
    FolderInbox
    Subject filterSupport
  4. Set the message sent to the agent when the trigger fires. Start with the simplest possible version, so you can see for yourself why it is not enough: 
    Use content from the email that just arrived.
  5. Save the trigger and Publish the agent. Copilot Studio builds a cloud flow behind the scenes — you will find it in Power Automate under the trigger's name.
You have just built something that acts without being asked. From this point the agent can send mail while you are not looking at it. If you need to stop it, turn the flow Off in Power Automate — unpublishing the agent is not the switch.
Stage 5 Test both paths~9 min

Two tests, and the second one is the important one.

Test 1 — it should answer

From your second address, send mail to the triggering mailbox. Put a real issue key in both the subject and the body:

Subject:  Support - give me details of issue having key ABC-1

give me full details of this issue having Key ABC-1

Expect a reply within a few minutes carrying the issue's real summary, type, project, status and priority. Check one field against Jira itself.

Test 2 — it should refuse

Now ask for something that does not exist. No key, nothing to look up:

Subject:  Support - need info on jira setup request

please give me details on the jira setup request

Expect a polite reply saying it could not find relevant information. Do not accept a plausible-sounding answer here. If it invents a ticket, that is the finding — the instruction did not hold, and you have learned more from this test than from the first one.

Run test 1 three times with identical text before you call it done. This shape is not deterministic, and one green run proves less than you think.

When nothing comes back

Work down this list in order. The first row catches most of it.

SymptomWhat is happeningWhat to do
The flow run says Succeeded and no mail arrived This is the normal case, not a contradiction. The trigger flow hands the prompt over and returns immediately — roughly 202 Accepted in under a second. It never learns what the agent did. Do not trust the flow's green tick. Open the agent's Activity / session transcript to see what it actually did with the message.
Same email, works sometimes The prompt in Stage 4 is vague, so the agent has to infer both the task and the ticket key from a raw message. Rewrite the trigger message to name the fields and state the task explicitly. See the next section.
Nothing triggers at all Subject filter not matched, or the flow is Off. The filter is a plain substring — Support matches "Support - …". Check the flow is On in Power Automate.
Jira call fails or returns the wrong site The Jira instance input was left for the model to fill. Go back to Stage 2 and pin it to a fixed value.
The reply goes to the wrong person Nothing constrains the recipient — the model chooses it. Expected behaviour of this build. See the next section.
It replies to its own replies Your reply goes out as "RE: Support — …". A response to that lands back in the Inbox and matches the filter again. Turn the flow off, then tighten the filter or move handled mail to another folder.

Before you use this for real

What you have built works, and it is deliberately the simple version. Six things stand between it and something you would let loose on a real support inbox. None of them is hard; all of them are invisible until they bite.

#GapThe fix
1Nothing checks the outcome. The flow reports success whether or not the agent replied. Have the flow wait for the agent instead of firing and forgetting, then branch on the response. Nothing calls this flow, so waiting is allowed here.
2The trigger message is vague. Handing over a whole raw email and hoping is what makes runs inconsistent. Pass the subject, body and sender as named values, with one sentence saying what to do with them.
3The recipient is chosen by the model. Bind the reply address to the sender of the triggering mail, the way you pinned the Jira instance.
4The refusal is reworded every run, and an unrecognised request never reaches it — it falls through to the product's stock "I'm not sure how to help with that." Put the refusal in a topic with fixed wording, and change the Fallback topic to return that wording too. A sentence in Instructions is a preference; a topic is a guarantee.
5It runs as whoever built it. Every requester gets the builder's Jira and mailbox visibility. Decide deliberately whose credentials each tool uses, and check what an agent shared with someone else would expose.
6Handled mail is not marked or moved, so there is no record of what was processed. Mark as read or move to a folder as the last step, and keep the session transcripts — they are the only place the whole conversation exists.
The one sentence to keep. A green run tells you a message was accepted. It does not tell you the work was done. An agent that acts without being asked needs something watching it that is not the thing that started it.
