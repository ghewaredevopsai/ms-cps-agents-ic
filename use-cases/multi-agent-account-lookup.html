Multi-Agent: Parent, Child, Connected

Build it yourself — Microsoft Copilot Studio
~40 minutes | No code | 1 parent · 1 child · 1 connected agent | Trainer: Rajesh Gheware
Use synthetic Account records. This agent reads customer rows out of Dataverse and repeats them back in chat. Build it against sample data or a table you have populated yourself — never against live customer records until you have worked through Before you use this for real at the end.

What you are building

Three agents, one conversation. A parent agent takes the question. It keeps some skills inside itself as a child agent, and delegates the rest to a separately published connected agent that queries Dataverse. The person typing sees one assistant.

The point of this build is not the data lookup — it is watching the orchestrator choose, at run time, which agent should handle a question, based only on the descriptions you wrote.

The distinction that decides everything

 Child agentConnected agent
Where it livesInside the parent. It has no separate existence.Its own agent, in the same environment.
PublishingPublished with the parent.Published on its own. The parent only ever sees its last published version.
ReuseBelongs to one parent.Any number of parents can connect to it.
Pick it whenYou are grouping instructions and tools for one job, managed by one person.A different team owns it, or you want it usable directly and by other agents.

Before you start

  • Copilot Studio, in an environment you are allowed to build in — and both agents must be in the same environment. Cross-environment connections are not supported.
  • Dataverse with rows in the Account table. Sample data is fine and is the fastest route (Power Platform admin centre → your environment → Settings → Data management → Sample data → Install).
  • Permission to turn on Dataverse search and to edit Quick Find views for the Account table.
  • Permission to create a Microsoft Dataverse connection. It is a premium connector — availability varies by licence, and that is a question for your admin rather than a blocker to reading on.
No knowledge sources are needed anywhere in this build. Both agents answer from a live table or from their own instructions.
Stage 1 Make Dataverse searchable~10 min

Do this first. Every later stage looks broken if you skip it, and the error you get will not mention search.

  1. In the Power Platform admin centre, open your environment → Settings → Product → Features.
  2. Under Dataverse search, turn on search indexing. Newer tenants show two checkboxes rather than one switch — tick the one that turns on indexing for search experiences, not only the AI one. Save.
  3. Go to make.powerapps.com → Tables → Account → Views and open Quick Find Active Accounts.
  4. Add the columns you want returned to the view: Address 1: State/Province, Address 1: ZIP/Postal Code, Annual Revenue, Currency.
  5. Now the step that actually matters — open Edit find table columns and add Address 1: City, Address 1: State/Province and Address 1: ZIP/Postal Code to Find by.
  6. Save and publish, and do not navigate away until it finishes. Then, from Solutions, run Publish all customizations.
View columns and find columns are not the same list. What the search can match on comes from Find by. What it can return comes from the view columns. Add a state to the view but not to Find by, and the agent will cheerfully tell you there are no accounts in that state.
Verify before moving on. The modern designer will not offer some address columns at all — if a column you need is missing from the picker, use Switch to classic on that view, which lists every one of them.
Stage 2 Build the lookup agent~12 min

This one becomes the connected agent. Build and prove it on its own before anything else points at it.

  1. In Copilot Studio choose Create → New agent, then Skip to configure. Name it Account Lookup.
  2. Give it a description. Other agents route on this text, so say what it is for: 
    Looks up account records — company name, city, state, postal code and revenue — from the sales system.
  3. Paste the Instructions: 
    You look up account records for sales colleagues.

Always use your account lookup tool to answer. Never answer from memory.
Report only the fields the tool returns. If the tool returns nothing, say
plainly that no matching account was found. Do not invent an account,
an address or a figure.
  4. Open Tools → Add a tool, search for Perform an unbound action, and choose the Microsoft Dataverse one. Create a connection when prompted, then Add and configure.
  5. Rename it Find Account and describe it — the parent's orchestrator reads this too: 
    Finds an account by city, state, postal code or account name.
  6. Set the first two inputs to Custom value:
    InputValue
    organizationPick your environment by name from the list — do not leave it on (Current).
    actionNamesearchquery — type it with Enter custom value if the list is empty.
  7. Use + Add input to add entities, set it to Custom value, and paste: 
    [{"name":"account","selectColumns":["name","accountid","address1_city","address1_stateorprovince","address1_postalcode","telephone1","emailaddress1","revenue"],"searchColumns":["name","address1_city","address1_stateorprovince","address1_postalcode"]}]
  8. Add search as an input, leave it on Dynamically fill with AI, and click Customize to give it a description. This sentence is what converts “Texas” into TX: 
    Search query that includes state in the format of two digit state code in all caps, 5 digit zip code, city, and/or the account name
  9. Save, then open the test pane and ask a question that uses the tool.
  10. Accept the consent prompt. The first real call raises a panel headed Microsoft Dataverse — This connection can…. Click Allow. Nothing works until you do.
  11. Go to Settings → Generative AI and turn on Let other agents connect to and use this one.
  12. Publish the agent.
Step 10 is the one that catches everyone. Until you click Allow, every call fails with HTTP 403 — connectorAuthorizationError, and the message blames the connection even though the connection is perfectly healthy. You can confirm the state under Settings → Connection Settings: before consent it reads “There are no permissions associated with this agent”.
Stage 3 Build the parent and its child agent~10 min
  1. Create a second agent named Sales Assistant with these Instructions: 
    You help sales colleagues find what they need.

Delegate product questions to the product agent, and any question about
an account, customer or company to the account lookup agent. Do not
answer account questions yourself. Keep replies short and factual.
  2. Open the Agents tab → Add an agent → New child agent. Name it Product Information.
  3. Give the child a description — this is the only thing the orchestrator uses to route to it: 
    Answers questions about our products: what they do, who they suit and how they differ from each other.
  4. Give the child its own instructions, and a knowledge source if you have one. Keep it deliberately narrow — a child that claims to do everything will steal questions meant for the connected agent.
  5. Publish the parent.
Notice what you did not do: the child agent was never published separately and has no settings page of its own. That is the whole difference between the two kinds.
Stage 4 Connect the two agents~5 min
  1. In Sales Assistant, go to Agents → Add an agent.
  2. Under Connect to an external agent, choose Copilot Studio, then pick Account Lookup from the list.
  3. Read the description it carries across, and sharpen it if it overlaps the child agent. This copy is local — later edits to the source agent's description will not flow through.
  4. Leave Pass conversation history to this agent ticked, so the lookup agent can see what was already asked.
  5. Add and configure, then Publish the parent again.
Not in the list? A connected agent only appears if it is (1) in the same environment, (2) published, and (3) has Let other agents connect to and use this one switched on. All three, not any one.
Stage 5 Test both paths~5 min

Test from the parent, never from the lookup agent. You are testing the routing, not the query.

Test 1 — should work
What are the accounts in Texas?

Open the activity map beside the answer. You should see the parent hand off to Account Lookup, which calls Find Account, which completes in about two seconds and returns real rows. Three hops, one answer.

Test 2 — should refuse
What is the credit rating of the largest account in Texas?

Credit rating is not in your selectColumns, so the tool cannot return it. A healthy agent says it does not have that field. An agent that answers anyway has just invented a number about a customer — and it will do that in front of a client too. If it invents, tighten the last line of the lookup agent's instructions and run it again.

Also worth trying: ask a product question and confirm it goes to the child agent instead. If both agents answer, or the wrong one does, your two descriptions overlap — fix the descriptions, not the instructions.

When nothing comes back

Work down this list in order. The first two rows catch nearly all of it.

SymptomWhat is happeningWhat to do
HTTP 403 — connector returned an authorization error The agent was never granted consent to use the connection — the message blames the connection, which is fine. Tools that arrive by importing a solution never raise the prompt at all. Run the tool from the test pane and click Allow. If no prompt appears, delete the tool and add it again from scratch — a freshly created tool raises it.
Action list is empty, or entities and search never appear as inputs Same cause — the designer is reading Dataverse metadata over that unconsented connection. Fix the consent first. The inputs appear under + Add input as soon as the schema can be read.
HTTP 400 — Required field 'search' is missing Consent is now fine and the call is reaching Dataverse — you are simply missing an input. Add search and entities as in Stage 2, steps 7 and 8.
“No accounts were found” but you can see the rows in the table Either the search term does not match the stored format (states are stored as TX, not Texas), or the column is not in Find by. Check the search input has the description from Stage 2 step 8, and re-check Stage 1 step 5.
An error naming a column you do not recognise Your selectColumns lists a column that does not exist in your environment — common when copying a definition from somewhere else. Remove it. Only stock Account columns are used in the block in Stage 2.
The parent answers account questions itself Routing, not plumbing. The parent's own instructions or the child's description are broad enough to swallow the question. Narrow the child's description and keep the parent's “do not answer account questions yourself” line.
Changes to the connected agent have no effect The parent uses the connected agent's last published version. Publish the connected agent after every change, then retest from the parent.

Before you use this for real

What you have built works. These are the gaps between it and something you would put in front of colleagues.

  • Everyone sees the maker's rows. The tool runs on maker-provided credentials, so every user gets the same results regardless of their own permissions. Row-level security in Dataverse is the fix, and it is a design decision rather than a switch.
  • Connected agents are one level deep. An agent that already has connected agents cannot itself be connected to a third.
  • Every hop costs latency. The parent orchestrates, then the connected agent orchestrates again — noticeably slower, for reasons the user cannot see.
  • Descriptions are the routing logic, and they are prose, so they degrade quietly as you add agents. Past roughly 30–40 choices an agent stops discriminating well; that, not tidiness, is the signal to split.
  • Nothing here is versioned. Instructions, descriptions and that entities block live only in the maker portal. Decide where the source of truth lives before a second person edits it.
