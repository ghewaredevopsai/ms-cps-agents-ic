Sales Associate Assistant

Build it yourself — one parent, two child agents, one topic
~40 minutes | No code | Microsoft Copilot Studio | Trainer: Rajesh Gheware

What you are building

One assistant, three things behind it. A topic asks which market you are in. Two child agents hold the product knowledge, and the condition on that variable decides which one is eligible. An already-published connected agent takes anything about an account. You build the parent only.
 Child agent — the two product agentsConnected agent — account lookup
LivesInside the parent, published with it.Its own published agent, reusable. The parent sees its last published version.
Chosen byA condition on Global.Market — deterministic.The orchestrator, weighing your description — not deterministic.
Fails byThe variable unset → neither child eligible. Debug the variable, not descriptions.Descriptions overlapping → the wrong agent answers. Rewrite the description, not the instructions.

Before you start

Copilot Studio, in an environment you can build in — plus the Account Data Lookup Agent already built and published there. It must satisfy all three of: same environment, published, and Let other agents connect to and use this one on. Confirm it answers What are the accounts in Texas? from its own test pane before you go on. Building it is a separate job with its own Dataverse prerequisites — follow microsoft/mcs-labs → mcs-multi-agent (also in resources.txt).

You also need a public website with different pages per market for the children's knowledge. This build uses microsoft.com and microsoft.com/en-gb. Nothing else — no Dataverse permissions, no premium connector, no flows.

Stage 1 Create the parent~8 min
  1. copilotstudio.microsoft.com → check the environment top right is the one your lookup agent lives in.
  2. Agents → chevron beside New agent → New classic agent. Name it Sales Associate Assistant. Leave the New experience toggle on.
  3. A classic agent starts blank. In Instructions select Edit and paste: 
    You are the Sales Associate Assistant. Your purpose is to help sales associates quickly find product information and look up account and contact information in the sales system.

Guidelines:
- Help sales associates get market-specific product information and answer account and contact questions.
- Only use the knowledge, tools, and connected or child agents configured on this agent. Do not rely on general model knowledge or the web.
- Ask the user which market they are working in when it is needed to scope product information.
- Delegate account and contact lookups to the connected account and contact agent.
- Keep responses concise, accurate, and grounded in the sources you are given.
- If you don't have the information, say so rather than guessing.
  4. Settings → Generative AI, bottom of the page: turn off both Use general knowledge and Use information from the Web. Save.
Step 4 is not housekeeping. Leave model knowledge on and the parent answers product questions itself, out of what it happens to know — and it looks right. Both children then appear to work while never being called.
Stage 2 The Select Market topic~10 min
  1. Topics → Add a topic → From blank.
  2. Leave the trigger on The agent chooses and fill in Describe what the topic does — see the warning below, this is the step that matters: 
    Ask the sales associate which market - US or UK - they want product information for. Use this whenever a product question is asked and the market is not yet known.
  3. Rename the topic to Select Market (top-left).
  4. + → Ask a question, message: 
    What market are you wanting information in?
  5. New option → US, then again for UK.
  6. Under Save user response as, select Var1 and rename it Market.
  7. In Variable properties: Usage → Global, tick External sources can receive value. Description: The market that the sales associate is requesting information about.
  8. Delete every Condition node the editor added under the question. You are storing the answer, not branching on it. Save.
  9. Second way in, for channels that support it: chevron beside the topic name → Conversation Start → add a node at the end → Topic Management → Go to another topic → Select Market. Save.
Do not make Conversation Start the only way in. Setting the topic to It's redirected to works in the Test pane and fails silently in Microsoft 365 Copilot, which invokes the agent straight with the user's message and raises no conversation-start activity. The topic never runs, the variable stays empty, neither child is eligible, model knowledge is off — and a plain product question returns “I'm not sure how to help with that.” Nothing errors; nothing is logged. Hence step 2: asking becomes the model's judgement, the gate stays deterministic.
Usage must be Global. A topic-scoped variable dies with the topic and will not appear in Stage 3's condition picker. If Global.Market is missing there, step 7 is why.
Stage 3 The two child agents~12 min
  1. Agents (top nav) → Add → New child agent. Name: US Product Information Agent.
  2. Description: 
    This agent provides details about the Surface products offered in the United States
  3. Expand Advanced, set Condition to Global.Market is equal to US.
  4. Instructions: 
    This agent should only answer questions about Microsoft Surface products in regards to the US-based products. It should never provide details or stats on any products not offered or details about models offered outside of the United States. You should only talk about Microsoft Surface products and not discuss any products that are not Microsoft Surface products even if they are made by Microsoft.
  5. In the child's own Knowledge section: Add → Public websites → microsoft.com → Add → Add to agent. Save.
  6. Repeat for the UK child, changing four things: name UK Product Information Agent, condition = UK, knowledge microsoft.com/en-gb, and United Kingdom / UK-based in place of United States / US-based in both the description and the instructions.
Both fields are needed and do different jobs: the condition decides whether the agent is eligible, the description decides whether the orchestrator picks it from those that are. Neither child is published separately or has a settings page, channel or URL — that is the whole difference from the connected agent.
Stage 4 Connect the Account Data Lookup Agent~5 min
  1. Agents → Add an agent → pick Account Data Lookup Agent.
  2. Read the description it brings across and sharpen it if it overlaps either child. This copy is local — later edits on the source agent do not flow through.
  3. Confirm Pass conversation history to this agent is ticked.
  4. Add and configure, then Publish.
Not in the list? It fails one of the three: same environment, published, Let other agents connect to and use this one on. All three are settings on that agent. What gets stored here is only a name and a description — which is why a change over there needs a publish before it is visible here.
Stage 5 Test — in the pane, then in a channel~5 min

Always from the parent. Open the activity map beside each answer — the hops are the result.

AskShould happen
Answer US, then Which Surface laptops can I offer? The US child answers. Reset, answer UK, ask again — the other child takes it. Same question, different branch, decided by the variable alone.
What are all of the details of accounts in Texas? Three hops: parent → connected agent → its tool, ~2 s. The description did that.
Fresh session; skip the market, ask the Surface question The parent should ask which market — step 2's description working, and the closest the pane gets to channel behaviour. It must not answer with the market unset.
Who is the contact at Alpine Ski House? Still the connected agent. If both answer, your descriptions overlap.
Then publish to a channel and repeat the first two

Not a formality: the pane raises a conversation-start activity on every new session and a channel may not, so the first test can pass in the pane and fail in the channel. If products fail there, ask the account question in the same channel. Accounts work, products do not → the published version is current, so it is the market variable: check the trigger is The agent chooses with a description. Both fail → not routing. Almost always the agent was never republished after your last change — the pane runs the draft, the channel runs the last publish. Check the published date before changing anything.

When nothing comes back

SymptomCauseFix
Anything works in the Test pane but not in a channel The pane runs the draft; a channel runs the last published version. A saved change is not a published change, and nothing warns you. Publish, then retest. Check the last published date before debugging anything else — it is the single most common cause of a pane/channel split.
Published, and the market is still never asked in a channel; every product question returns “not sure how to help” No conversation-start activity in that channel, so a redirect-only topic never ran. The variable stays empty, no child is eligible, and model knowledge is off. Trigger → The agent chooses, with a description (Stage 2 step 2). Keep the redirect too. Republish and retest in the channel.
The topic is skipped when the user's message already names a market The model judges “the market is known” from the conversation, not from the variable — so it skips the topic and Global.Market stays empty. A user saying “US” sets nothing. Point the description at the variable, not at knowledge: …has not yet been set in this conversation, including when the user names a market, because that does not set the variable.
Global.Market is missing from the condition picker The variable is topic-scoped. Stage 2 step 7 — Usage → Global, save, reopen the child.
Neither child answers; the wrong child answers The variable is empty for this session, or a condition points at the wrong value. Check the variable first. Compare both children's Advanced sections. Do not touch descriptions.
The parent answers questions itself instead of delegating For products: Use general knowledge is still on, so it never needed a child. For accounts: the hand-off line is missing or the connected agent's local description is vague. Stage 1 step 4; or keep the “Delegate account and contact lookups…” line and sharpen the description.

Before you use this for real

  • A condition is only as good as what sets it — and this one has already bitten. Publishing to Microsoft 365 Copilot skipped the market question and both children dropped out of every turn; agent-to-agent calls and unattended triggers do the same. When you add a surface, ask not does it answer but what still sets the variables it gates on.
  • Everyone sees the same rows. The lookup agent's tool runs on credentials you do not control from here, so results may not be trimmed per asker. Dataverse row-level security is the fix, and a design decision.
  • Descriptions are routing logic in prose and degrade quietly as you add agents — past roughly 30–40 choices an agent stops discriminating well. Conditions do not, which argues for using them wherever the answer is genuinely deterministic. Connected agents are also only one level deep, and none of this is versioned: instructions, descriptions and both conditions live only in the maker portal.
