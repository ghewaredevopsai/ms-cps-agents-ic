The Render Endpoint

Slide plan in, PowerPoint out — an Azure Function in Python
~45 minutes | Python 3.11 | One dependency | Trainer: Rajesh Gheware
This is the box behind Tool 6. It is the last hop of the Fund Research Assistant build — Stage 7's Build Review Deck and Stage 8's trigger flow both POST a slide plan here and get a .pptx back. Nothing on this page is AI: it is ordinary application code, and the whole point is that the interface is the plan, so your team can replace this with whatever generator you already own.

What you are building

An HTTP endpoint that turns JSON into a PowerPoint file. One route, one POST, raw .pptx bytes in the response body. It has no state, no database and no knowledge of Copilot Studio — which is exactly why the agent can be pointed at it, or at something else, without either side caring.

Before you start

  • An Azure subscription you can create resources in. The Consumption plan's free grant covers this comfortably.
  • Python 3.11 locally — match the runtime you will deploy to, or you will debug a version difference instead of your code.
  • Azure CLI (az) and Azure Functions Core Tools v4 (func).
  • plan-to-pptx.py and slide-plan-sample.json from the demo assets.
You do not need any of this to finish the agent build. Stage 7 of the agent page gives two offline routes — run plan-to-pptx.py by hand, or open deck-renderer.html in a browser. Host it only when you want the chain to run with nobody at the keyboard, which is what Stage 8 is for.
Stage 1 Scaffold it locally~8 min
What this proves: the whole thing runs on your laptop first. Deploying is the last step, not the first.
  1. Create the project. The v2 programming model is the current one — a single function_app.py with decorators, no per-function folders or function.json: 
    mkdir plan-to-pptx && cd plan-to-pptx
func init . --python --model V2
  2. Declare the dependencies. Two lines — that is the entire supply chain: 
    azure-functions
python-pptx
  3. Copy plan-to-pptx.py into the project folder, beside function_app.py. You are going to import it, not rewrite it — its build(plan, out) already does the work, and keeping one renderer means the hosted and offline routes cannot drift apart.
  4. Create the virtual environment and install: 
    python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
Stage 2 The handler — about thirty lines~10 min
What this proves: the endpoint is a thin wrapper. All the real work already existed as a script.

Replace function_app.py with this:

import io
import json
import logging

import azure.functions as func

from plan_to_pptx import build          # the script you copied in, unchanged

app = func.FunctionApp()

PPTX = "application/vnd.openxmlformats-officedocument.presentationml.presentation"


@app.route(route="render", methods=["POST"], auth_level=func.AuthLevel.FUNCTION)
def render(req: func.HttpRequest) -> func.HttpResponse:
    try:
        plan = req.get_json()
    except ValueError:
        return func.HttpResponse("body must be JSON", status_code=400)

    if not isinstance(plan, dict) or "slides" not in plan:
        return func.HttpResponse("expected a slide plan with a 'slides' list", status_code=400)

    buf = io.BytesIO()
    try:
        count = build(plan, buf)
    except Exception:
        logging.exception("render failed")
        return func.HttpResponse("could not render this plan", status_code=500)

    logging.info("rendered %d slides", count)
    return func.HttpResponse(buf.getvalue(), mimetype=PPTX, status_code=200)
Do not add a Content-Disposition header with the deck's title in it. This is the bug that cost a live run. HTTP headers are Latin-1 only; the agent titled a deck with an em-dash, the header could not encode it, and the function returned 500 — while every local test passed, because every local test used the tidy ASCII sample. The flow names the file anyway, so the header buys nothing. If you want one, normalise first: title.encode('ascii', 'ignore').decode().
Two small things that matter. plan-to-pptx.py must be imported as plan_to_pptx — rename the file or add a shim, because a hyphen is not valid in a module name. And build() takes a path in the script; prs.save() accepts a file-like object just as happily, which is why io.BytesIO() works without touching the renderer.
Stage 3 Run it on your laptop and prove it works~7 min
What this proves: if it fails after deployment, you will know it is the deployment and not the code.
  1. Start the runtime. It prints the local route: 
    func start
  2. Post the sample plan and keep what comes back: 
    curl -s -X POST http://localhost:7071/api/render \
     -H "Content-Type: application/json" \
     --data @slide-plan-sample.json \
     -o local.pptx
file local.pptx
  3. file should say a Microsoft PowerPoint / OOXML document. Open it. A file of the right size that PowerPoint refuses is still a failure.
  4. Then post something that is not the tidy sample. Edit deck_title in the JSON to contain an em-dash and a rupee sign and post it again. This is the test that would have caught the bug above.
Check
  • local.pptx opens, seven slides, a native chart and a real table.
  • Every figure carries its source line, and the closing slide lists whatever was in unresolved.
  • Post {} and you get 400, not a stack trace. Post malformed JSON and you get 400 too.
Stage 4 Create the Azure resources~8 min
What this proves: three commands, and the names are the only decisions.
LOC=centralindia
RG=rg-render-endpoint
STG=strender$RANDOM                 # storage names: lowercase letters and digits, 3-24 chars, globally unique
APP=fn-render-$RANDOM               # the function app name becomes the hostname, so it is global too

az group create -n $RG -l $LOC

az storage account create -n $STG -g $RG -l $LOC --sku Standard_LRS

az functionapp create -g $RG -n $APP \
  --storage-account $STG \
  --consumption-plan-location $LOC \
  --runtime python --runtime-version 3.11 --functions-version 4 \
  --os-type Linux
Both names are globally unique, so a plain fn-render will collide with somebody else's. The $RANDOM suffix is not decoration. Keep the whole thing in one resource group and teardown is a single command — see the end of this page.
Stage 5 Deploy, and get the key~7 min
What this proves: the same bytes that worked locally now answer from the internet — and only to a caller holding the key.
  1. Publish. Core Tools builds the dependencies remotely, which is what you want — python-pptx then matches the host's platform rather than your laptop's: 
    func azure functionapp publish $APP --build remote
  2. Read the function key back. Treat what this prints as a credential — it is the only thing standing between your endpoint and the open internet: 
    az functionapp function keys list -g $RG -n $APP --function-name render -o tsv

    If that returns nothing, the host key works too: az functionapp keys list -g $RG -n $APP --query functionKeys -o tsv.

  3. Test the deployed endpoint exactly as you tested the local one: 
    curl -s -X POST "https://$APP.azurewebsites.net/api/render" \
     -H "Content-Type: application/json" \
     -H "x-functions-key: <the key>" \
     --data @slide-plan-sample.json \
     -o hosted.pptx
file hosted.pptx
  4. Call it once without the key and confirm you get 401. An endpoint you have not tried to break is an endpoint you are guessing about.
The first call after idle will be slow. On the Consumption plan the app scales to zero, so a cold start of several seconds is normal and is not a fault. It matters here: a flow called by an agent has roughly 100 seconds in total, and a cold start eats into it. If that becomes tight, warm it or move off Consumption — do not shorten the plan.
Stage 6 Point the flow at it~5 min
What this proves: the agent side needs one URL and one header, and nothing about the renderer leaks into it.

Back in the agent build, Stage 7, Tool 6 — the HTTP action takes:

FieldValue
MethodPOST
URIhttps://<your-app>.azurewebsites.net/api/render
HeadersContent-Type = application/json
x-functions-key = the environment variable, not the literal — the recipe is on the agent page
Body@json(triggerBody()?['text'])
Stage 8's trigger flow posts the same way, except its body is the agent's reply sliced between the two markers. Neither flow knows anything about Python, which is the property worth keeping.

When it does not work

SymptomCauseFix
500 on the agent's plan, 200 on the sampleNon-ASCII in a string you put into a header. The agent writes em-dashes; your fixture does not.Drop the Content-Disposition header, or normalise the value. Always test with the agent's own output.
ModuleNotFoundError: plan_to_pptxThe file is still called plan-to-pptx.py. A hyphen is not valid in a module name.Rename it to plan_to_pptx.py.
Works locally, 500 once deployedpython-pptx was built for your laptop's platform.Republish with --build remote.
401 from the flowThe x-functions-key header resolved to null — usually the environment-variable name is wrong.It is display name, space, schema name in brackets, exactly. Test the URL with curl and the literal key first to prove the endpoint is fine.
The flow saves a file that will not openCreate file is writing the wrong thing — often an error page, saved as .pptx.Open the flow run and read the HTTP action's output. A renderer that returns JSON on error will have that JSON saved as a deck.
Timeouts under the agentCold start plus render time against the ~100-second agent-to-flow ceiling.Warm the app, or move the render behind the approval as Stage 8 does — nothing is waiting on it there.
Deployment succeeds, route 404sThe v2 model needs function_app.py at the project root, and the route name must match.func azure functionapp list-functions $APP — if it lists nothing, the file was not found.

Before you use this for real

GapThe fix
A function key is a shared secret in a header, and everyone who can open the flow can read it.A Key Vault-backed Secret environment variable, or put the endpoint behind Entra ID and call it with a managed identity.
Anyone with the key can post anything. There is no size limit and no schema validation beyond one key check.Validate the plan against the schema before rendering, and cap the request body.
It is open to the internet.VNet integration and a private endpoint, or an IP allow-list, if the plans carry anything real.
Nothing tells you when it fails except a flow run somebody happens to read.Turn on Application Insights and alert on the failure rate. It is a checkbox at creation time and a retrofit afterwards.
The renderer is a copy.Keep one plan_to_pptx.py in source control and deploy it, so the hosted and offline routes cannot diverge.
Tear it all down when you are finished — one command, because everything went into one resource group: 
az group delete -n $RG --yes --no-wait
